## D-001 产品从飞影批量工具升级为 AI 数字人内容生产 SaaS

- **日期**：2026-08-04
- **决策**：正式产品定位升级为「面向电商运营团队的 AI 数字人内容生产 SaaS」，覆盖商品与营销目标、文案生成与质检、数字人/声音/背景素材、视频方案审核、批量生产、成片质检、交付与发布管理的完整工作流。
- **原因**：用户购买的是生产结果而非网页自动化；仅作为飞影批量工具会限制产品边界与商业空间。
- **影响**：新建 `docs/product/` 产品文档体系；后续 Epic 按 SAAS-001 系列拆分；产品语言全面转向运营视角。
- **被否决方案**：继续维持「飞影网页批量自动化工具」定位，只做功能增强。
- **可重新评估条件**：目标市场或商业模式发生根本变化，由 owner 重新决策。

## D-002 飞影作为 Provider，不作为上层领域模型

- **日期**：2026-08-04
- **决策**：飞影只是底层视频生成供应商之一；上层领域模型不使用飞影按钮文案、页面 selector 或具体网页步骤作为领域概念。
- **原因**：产品上层与单一供应商页面结构永久绑定会导致不可维护与不可替换。
- **影响**：引入 Provider Adapter 抽象（Hifly Playwright/API、影刀可选、其他平台）与 capability 模型。
- **被否决方案**：以飞影页面流程直接作为产品领域模型。
- **可重新评估条件**：飞影正式开放完整 API 且成为唯一供应商时，可评估简化 Adapter 层（仍需保留抽象）。

## D-003 保留并下沉现有可靠执行内核

- **日期**：2026-08-04
- **决策**：现有批量执行内核（状态机、原子写、幂等、证据、CI 标准）保留并下沉为 Local Execution Agent / Provider Execution Engine，不推翻、不删除。
- **原因**：执行内核是已验证的资产；重写将引入不可控风险并浪费既有稳定性投入。
- **影响**：batch/task 保留为执行层工作单；产品层通过编译边界（compileApprovedVideoPlansToBatch）与执行层衔接。
- **被否决方案**：推倒重来，用新执行系统替换现有内核。
- **可重新评估条件**：执行内核出现无法修复的架构性限制，且替代方案有充分验证。

## D-004 采用云端 Control Plane + Local Agent

- **日期**：2026-08-04
- **决策**：架构采用云端 SaaS Control Plane 与本地/VPS Local Agent 分离；长时 Playwright 任务不进入 Serverless/Workers 请求生命周期。
- **原因**：浏览器长任务、本地文件、登录态与人工接管都要求常驻本地执行环境；云端适合编排、状态与商业信息。
- **影响**：AGENT-001 规划 Agent 协议；云端不保存不必要的飞影 Cookie。
- **被否决方案**：纯云端 Serverless 执行 Playwright；纯本地单机产品（无云端控制面）。
- **可重新评估条件**：Provider 全面开放 API 且无需浏览器执行时，可评估 Agent 轻量化。

## D-005 产品主流程采用五阶段

- **日期**：2026-08-04
- **决策**：统一阶段导航固定为：1 商品与目标 → 2 文案与质检 → 3 人物与素材 → 4 视频方案 → 5 生成与交付。
- **原因**：五阶段与运营的真实生产过程对齐，是产品语言与技术执行之间的稳定边界。
- **影响**：项目内导航、领域模型分组、用户流程文档全部按五阶段组织。
- **被否决方案**：按技术模块（上传/执行/下载）组织主流程；自由画布式无阶段流程。
- **可重新评估条件**：用户研究发现阶段划分显著违背目标用户心智，由 owner 决策调整。

## D-006 第一阶段不自研数字人基础模型

- **日期**：2026-08-04
- **决策**：第一阶段通过 Provider 完成数字人/声音/视频能力（公共数字人、照片数字人、复刻、AI 生成、声音克隆、对口型、换背景等），不自研基础模型。
- **原因**：基础模型训练成本与周期远超产品当前阶段；上层价值在资产建模、编排、审核与交付。
- **影响**：SaaS 层聚焦资产建模/选择/配置/编排/跟踪/登记/审核/交付；能力可用性受 Provider capability 约束。
- **被否决方案**：自研数字人生成模型作为第一阶段核心。
- **可重新评估条件**：商业规模与团队能力达到模型投入门槛，由 owner 重新决策。

## D-007 影刀仅作为可选 Adapter

- **日期**：2026-08-04
- **决策**：影刀可作为可选 Adapter，但不能成为产品领域模型和核心执行协议的唯一基础；产品主链路不绑定只有 Windows 能稳定运行的低代码 RPA。
- **原因**：跨平台（macOS/Windows/后续 Linux）是产品竞争力；单一 RPA 依赖带来平台与供应商双重锁定。
- **影响**：核心执行协议自建（Agent 协议 + Provider Adapter）；影刀仅在特定场景补充。
- **被否决方案**：以影刀为唯一执行器快速搭产品。
- **可重新评估条件**：影刀提供跨平台稳定执行与正式集成契约，可评估提升其适配层级（仍非唯一）。

## D-008 运营产品语言与技术执行状态分离

- **日期**：2026-08-04
- **决策**：运营界面使用生产结果语言（待生成/生成中/已完成/需人工处理等）；技术状态（Playwright、batch.json、executor、snapshot、queue、lock、capture HTTP 等）收敛到任务详情、诊断页面与本地执行器页面。
- **原因**：运营人员购买生产结果，不理解也不应被要求理解执行内部机制。
- **影响**：增加业务状态映射层；信息架构中运营区与技术区隔离；内部 pointBudget 不作为用户术语。
- **被否决方案**：直接把底层状态机状态展示给运营用户。
- **可重新评估条件**：无（原则性决策）；映射层细节可迭代。

## D-009 VideoPlan 是业务计划，batch/task 是执行工作单

- **日期**：2026-08-04
- **决策**：新产品层中 VideoPlan 是业务真相；现有 batch/task 是执行层工作单；batch 不直接暴露为用户项目，用户不修改底层 execution 状态；两者经编译边界衔接并建立双向追踪 ID。
- **原因**：业务计划需要版本、审核、变体等语义；执行工作单需要原子、幂等、证据等语义；二者混用一个模型会互相破坏。
- **影响**：规划 compileApprovedVideoPlansToBatch() 编译边界；领域模型多状态域分离。
- **被否决方案**：直接扩展 batch 结构承载全部业务语义；或废弃 batch 另建执行系统。
- **可重新评估条件**：编译边界实现后发现追踪模型不足，可在不改变「业务/执行分离」前提下调整实现。

## D-010 产品化与底层稳定性工作可以并行

- **日期**：2026-08-04
- **决策**：SaaS 产品化（SAAS-001 系列）与底层稳定性工作（CORE/CI 系列）可并行推进，但互不搭车：各自独立分支、独立 PR、独立审查。
- **原因**：稳定性是产品化的前提之一，等待串行完成会拖慢整体；搭车合并会破坏 PR 可审查性。
- **影响**：PR 治理保持「独立分支、无搭车合并」；产品 PR 不修改执行内核，稳定性 PR 不引入产品概念。
- **被否决方案**：先完全结束稳定性工作再开始产品化；或在同一 PR 混合两类变更。
- **可重新评估条件**：无（流程性决策）；具体并行节奏由 owner 按资源调整。

## D-011 数字人、声音和人物源素材的授权与敏感资产保护底线

- **日期**：2026-08-04
- **决策**：用户照片、视频、声音和数字人复刻源素材属于敏感资产，产品必须满足以下底线：
  1. 未记录有效授权，不得：创建数字人、克隆声音、上传 Provider、创建对口型任务、创建生产任务；
  2. 授权失效、撤销或资产 disabled 后：新任务 Preflight 必须 fail-closed，不得继续创建新的 Provider 任务；
  3. 资产的创建、使用、撤销、删除需要审计留痕；
  4. 云端和 Local Agent 只处理任务需要的最小数据；
  5. 普通运营不能通过修改前端字段绕过授权状态；
  6. Provider Adapter 在真实上传前必须重新校验授权状态；
  7. 具体授权材料形式、保留期限、删除时限和法律文本仍为开放问题，保留在 Q-007 / Q-008，不得擅自决定；
  8. 资产可用状态（asset.status）与授权状态（authorization.status）分离建模，两者同时满足才能通过生产 Preflight。
- **原因**：数字人/声音复刻涉及人格权与合规风险；授权缺位下的生产与上传会造成不可逆的法律与信任损失，必须在产品模型层 fail-closed，而不是依赖运营自觉。
- **影响**：领域模型新增 AuthorizationRecord / ConsentEvidence / AuthorizationRevocation / DeletionRequest / AuditEvent 规划（见 [DOMAIN_MODEL.md](DOMAIN_MODEL.md) 第七节）；Preflight 增加授权校验项；Provider Adapter 上传前强制重校验；蓝图新增原则 6。
- **被否决方案**：仅在运营文档中提示授权重要性而不做系统强制；把授权材料与业务数据混合存储、事后补录。
- **可重新评估条件**：授权材料形式与法律文本（Q-007/Q-008）确定后可细化实现；「fail-closed + 审计留痕 + 最小数据」底线本身不重新开放。

## D-012 Provider Task Router：API Worker + Local Agent 双执行路径

- **日期**：2026-08-04
- **决策**：长期执行架构不要求所有任务都经过 Local Agent。引入 Provider Task Router：已确认 API 能力由 Hifly API Worker 处理；仅网页支持、登录态、本地文件和人工接管能力由 Local Agent / Playwright 处理。API 创作任务必须异步执行，不放在普通 HTTP 请求生命周期内。
- **原因**：飞影数字人 API V2 文档已确认 14 项能力在文档层面存在（账号权限与真实调用仍待确认）；API 能力在权限与验证具备后无需依赖浏览器自动化，而登录态、本地文件与人工接管能力仍必须留在 Local Agent。这是对 D-004 的细化而非推翻：长任务不进请求生命周期的约束保持不变。
- **影响**：`PROVIDER_AND_AGENT_ARCHITECTURE.md` 第四节（任务路由）与第六节（API 调研五层确认）更新；回调不能作为唯一完成机制，必须配合轮询对账（provider task id / request id / callback received time / last poll time / 主动对账）；Token 保管位置由 Q-018 决策，决策前不得默认上传云端。
- **被否决方案**：所有任务一律经过 Local Agent；API 创作任务同步放入请求生命周期。
- **可重新评估条件**：飞影 API 账号权限与真实调用验证结果决定 API Worker 承接能力的范围；「长任务不进请求生命周期」「Local Agent 保留仅网页/登录态/人工接管能力」原则不重新开放。

## D-013 Hifly-first Provider 策略（Hifly-first，不是 Hifly-only）

- **日期**：2026-08-04
- **决策**：正式表述为 **Hifly-first，不是 Hifly-only**。在飞影满足以下条件时，优先使用飞影完成数字人、声音、普通数字人口播、音频驱动、对口型、背景处理和相关视频能力：
  1. 功能覆盖满足产品需求；
  2. 真实效果质量达标；
  3. 自动化路径稳定；
  4. 成本和生成时延可接受；
  5. 能取得稳定 task ID、状态、结果和失败信息；
  6. 可安全重试、对账和恢复；
  7. 满足授权与敏感资产要求（D-011）。

  执行路径偏好顺序：

  ```text
  1. 飞影正式 API
  2. 飞影 Playwright
  3. 飞影人工接管的半自动流程
  4. 其他 Provider
  ```

  但这不是无条件强制：当其他 Provider 在关键功能、质量、稳定性、成本或合规上明显更优时，可以经相同 Provider Adapter 接入。**未经 capability 实际调研与验证，不得宣布飞影支持该能力。**
- **原因**：优先单一主 Provider 可以减少运营配置、减少数字人和声音资产迁移、减少多供应商 Token 与账号管理、保持人物、声音和作品链路一致；同时保留 Adapter 抽象避免 Hifly-only 锁定。
- **影响**：第一版普通运营界面**不要求用户选择 Provider**——用户选择的是生产结果类型，Provider Task Router 根据已验证能力路由；Provider 选择只进入高级设置、管理员配置或技术诊断区域。capability 确认表（`PROVIDER_AND_AGENT_ARCHITECTURE.md` 第九节）是路由与排期的依据。
- **被否决方案**：Hifly-only（禁止其他 Provider 接入）；多 Provider 完全对等、由运营在首版界面自由选择。
- **可重新评估条件**：飞影某能力不满足上述七项条件时，该能力可经 Adapter 接入其他 Provider；「Hifly-first 偏好 + Adapter 抽象不绑定」的框架本身不重新开放。

## D-014 企业内部目标用户与产品边界

- **日期**：2026-08-04
- **决策**：第一批目标用户是**企业内部的电商运营、内容生产、内容审核和管理团队**。产品属于**企业内部 AI 数字人内容生产平台**，不是面向公众自助购买的通用消费者 SaaS。第一版优先服务单一企业、单一组织，但领域模型保留 Organization 边界，不得把全部数据永久建模为无组织归属的全局数据。核心价值：企业内部项目与商品管理、文案生成/版本与审核、数字人/声音和敏感资产管理、视频方案审核、批量生产、失败处理、作品交付、内部用量/成本和审计。
- **原因**：企业内部场景可以聚焦生产链路与治理能力，避免公众自助购买场景的获客、支付与合规复杂度；同时保留组织边界为后续多组织扩展留余地。
- **影响**：**关闭 Q-001**；组织、权限、授权、审计仍然重要；产品不再以公众自助购买和套餐转化为设计中心。
- **被否决方案**：面向公众自助购买的通用消费者 SaaS；完全无组织归属的全局数据模型。
- **可重新评估条件**：owner 决定开放公众自助注册与购买时，重新评估产品边界与商业化范围（仍不与 D-016 的内部治理定位自动冲突，需另行决策）。

## D-015 Cloud-first，Tencent Cloud first

- **日期**：2026-08-04
- **决策**：第一版产品就是**可以通过浏览器访问的 Cloud-first Web Control Plane，默认部署目标为腾讯云**。用户通过云端 Web 产品完成：登录、项目管理、商品与文案、人物与素材、VideoPlan、审核、任务查看、作品管理。依赖网页登录态、本地文件、Playwright、下载和人工接管的能力，仍由 Local Agent 或常驻执行节点承担。正式表述：**Tencent Cloud first，不是 Tencent Cloud only**。要求：
  1. 业务领域模型不得依赖具体腾讯云产品名称；
  2. Database、ObjectStorage、Queue、SecretStore 使用基础设施抽象；
  3. 腾讯云只作为第一版默认部署实现；
  4. 具体腾讯云数据库、对象存储、队列、密钥管理和部署服务仍待 Q-021 决定；
  5. 不得在本轮选择具体腾讯云产品。
- **原因**：云端 Web 形态让企业内部团队通过浏览器即可协作使用；腾讯云是 owner 选定的第一版部署目标；领域层与具体云厂商解耦保持可迁移性。
- **影响**：**关闭 Q-002**（第一版提供云端 Web 登录）；**关闭 Q-013**（第一版先做单企业/单组织云端 MVP）；**收窄 Q-014**（云厂商确定为腾讯云，具体服务仍开放）；调整 DELIVERY_ROADMAP 的 Phase 顺序（云端 Control Plane 提前进入 Phase 1）。
- **被否决方案**：Local-first 桌面/单机优先形态；本轮直接选定具体腾讯云产品。
- **可重新评估条件**：Q-021 确定具体腾讯云服务后细化部署设计；「Cloud-first + 领域层不绑定具体云产品」框架本身不重新开放。**不得根据 owner 提到的 WenrongAI 推测其技术栈**——只记录 owner 明确选择的「腾讯云部署 + 云端 Web 产品形态」。

## D-016 企业内部使用，不建设支付和套餐

- **日期**：2026-08-04
- **决策**：产品主要供企业内部使用。当前产品路线**不建设**：支付、套餐、订阅、账单、充值、余额、优惠券、续费、面向客户的自动计费。**仍保留**：企业内部任务用量、Provider 消耗、LLM 调用量、成本估算、内部预算和限额、成员使用情况、审计日志、异常消耗告警。将现有 **COMMERCIAL-001** 统一调整为 **ENTERPRISE-001：企业权限、治理、内部用量与审计**。不得删除 UsageRecord、CostEstimate 等内部治理所需模型，但必须移除套餐、账单和付款语义。
- **原因**：企业内部平台的治理需求（用量、成本、限额、审计）与面向客户的收费系统（支付、套餐、账单）是两类不同问题；当前阶段只需要前者。
- **影响**：DELIVERY_ROADMAP 的 COMMERCIAL-001 改为 ENTERPRISE-001；DOMAIN_MODEL 移除 Plan/Subscription/Billing/Payment/Package/Balance 等纯收费实体或标记为非目标；保留并重新解释 UsageRecord/CostEstimate/Quota/Budget 为内部治理用途；信息架构移除套餐中心/支付/账单入口。
- **被否决方案**：保留完整商业化（支付/套餐/账单）作为第一版范围；删除全部用量与成本模型。
- **可重新评估条件**：owner 决定面向外部客户收费时，另行决策恢复商业化范围；「内部用量与成本治理保留」不重新开放。

## D-017 人物步骤同时支持创建新人物和选择现有人物

- **日期**：2026-08-04
- **决策**：产品的人物步骤统一表达为「**创建新人物或选择现有人物**」。产品入口至少规划：公共数字人、企业已有数字人、创建新人物。但第一条端到端黄金路径和图片数字人创建**必须拆开实施**。
  - **Phase 1A 黄金路径**：云端登录 → 创建项目 → 上传商品 → 生成和质检文案 → 选择公共或已有数字人 → 创建并审核 VideoPlan → 编译为现有 batch → 当前手里有货执行 → 作品库交付。
  - **Phase 1B 独立人物创建子切片**：上传人物图片 → 检查有效授权 → 创建飞影图片数字人异步任务 → 查询或接收任务状态 → 获取 Provider avatar 标识 → 登记 AvatarAsset → 回到统一人物选择流程 → 用于 VideoPlan。
  要求：Phase 1A 不依赖 Phase 1B 完成；不得把图片数字人创建、授权、上传、异步任务和完整主链路塞进一个大 PR；创建人物必须继续遵守 D-011；未记录有效授权不得上传 Provider 或创建数字人；新人物创建可能产生 Provider 消耗，开发前必须获得 owner 对真实调用的单独授权。
- **原因**：黄金路径先用已有/公共人物打通端到端，风险最低；图片数字人创建涉及授权、异步任务与 Provider 消耗，独立切片实施可控。
- **影响**：**关闭 Q-016**，并将上述两层切片作为正式结论记录；USER_FLOWS 增加 Flow A（选择已有/公共人物黄金路径）与 Flow B（创建图片数字人）；DOMAIN_MODEL 规划 AvatarCreationTask；DELIVERY_ROADMAP Phase 1A/1B 拆分。
- **被否决方案**：把图片数字人创建与黄金路径合并为一个大切片；人物步骤只支持选择或只支持创建。
- **可重新评估条件**：Phase 1A 交付后可启动 Phase 1B；D-011 授权底线与「真实调用需 owner 单独授权」不重新开放。

## D-018 飞影多能力是正式产品路线

- **日期**：2026-08-04
- **决策**：以下能力属于**正式产品路线**，不是可有可无的实验项：当前手里有货、公共数字人、公共/自有声音、普通文本数字人口播、音频驱动数字人口播、图片数字人创建、视频数字人复刻、声音克隆、通用对口型、视频背景替换、其他经过调研确认的飞影能力。但每项能力必须严格通过五层状态：1. API 文档已确认；2. 当前账号权限已确认；3. 真实调用已验证；4. Adapter 已实现；5. SaaS 产品能力已完成。**不得因为它属于正式路线，就提前宣布已经支持。** HIFLY-001 推荐调研和接入顺序：
  0. 保留当前手里有货 Playwright 能力
  1. 公共数字人列表
  2. 公共/自有声音列表
  3. 文本驱动普通数字人口播
  4. 音频驱动普通数字人口播
  5. 图片数字人创建
  6. 声音克隆
  7. 视频数字人复刻
  8. 通用对口型
  9. 视频背景替换
  10. 手里有货背景和场景来源

  这个顺序是当前规划优先级，不代表账号权限和真实调用已验证。
- **原因**：明确正式路线避免能力被当作实验项随意砍掉；同时五层状态与 Evidence 台账防止未验证能力被提前宣布。
- **影响**：**收窄但不关闭 Q-005**（产品目标和优先级已确定，第一批实际实现范围仍需结合账号权限与 HIFLY-001 Evidence 决定）；新增 [HIFLY_CAPABILITY_EVIDENCE.md](HIFLY_CAPABILITY_EVIDENCE.md) Evidence 台账按此顺序记录；DELIVERY_ROADMAP Phase 3 按此顺序逐项推进。
- **被否决方案**：把飞影多能力列为可选实验项；因属于正式路线而跳过五层确认直接宣布支持。
- **可重新评估条件**：账号权限与真实调用验证结果可调整接入顺序；「五层状态 + Evidence 先行」原则不重新开放。

## D-019 文案生成与质检属于 SaaS 自有业务能力

- **日期**：2026-08-04
- **决策**：文案生成、版本管理、品牌规则、质检和审核属于 **SaaS 自有业务能力**，不得永久依赖飞影网页内置文案功能。架构采用：
  ```text
  CopyGenerationService
          ↓
  LLM Provider Adapter
  ```
  至少预留：平台默认模型、企业自有 API Key、可替换 Provider、可配置 base URL、可配置 model。普通运营用户只看到「生成文案」和业务配置，不要求其理解 LLM Provider、base URL 或 API Key。飞影内置文案功能可以作为：效果对比参考、特定模板辅助能力、未来经过正式接口验证后的可选 CopyProvider——但不能成为阶段二业务真相。
- **原因**：文案是阶段二的业务真相，必须掌握在 SaaS 自有能力中；依赖飞影网页内置功能会让核心业务受制于供应商页面变化。
- **影响**：**Q-003 收窄为**：LLM Adapter 架构已决定；默认 Provider 和默认模型仍待 Q-019 决定。**Q-004 保持开放**：规则、品牌规范、LLM 语义评估和人工审核的权重仍未决定。DOMAIN_MODEL 规划 LlmProviderConfig；PROVIDER_AND_AGENT_ARCHITECTURE 增加 LLM Provider Adapter 分层。
- **被否决方案**：永久依赖飞影网页内置文案功能作为阶段二业务真相；本轮即选定具体 LLM Provider/模型。
- **可重新评估条件**：Q-019 确定默认 Provider/模型后细化实现；「文案为 SaaS 自有能力 + LLM Adapter 抽象」框架不重新开放。

## D-020 MVP 平台默认凭证，后续企业 BYOK

- **日期**：2026-08-04
- **决策**：MVP 阶段使用 owner 在部署环境中安全配置的**平台默认 LLM API Key**。产品文档和代码中统一称为「**平台默认凭证**」。不得把领域模型永久绑定到个人身份或「owner 私人 Key」。MVP 普通用户无需配置 API Key 即可使用文案功能。后续企业版本：企业管理员可以在高级设置中选择使用平台默认模型或使用企业自有 API Key。**企业 BYOK 是组织级配置，不是每个普通运营用户单独配置。** 安全底线：
  1. 真实 Key 不进入前端代码；
  2. 真实 Key 不提交 GitHub；
  3. 真实 Key 不写入 Markdown；
  4. 真实 Key 不出现在日志；
  5. 真实 Key 不出现在错误信息；
  6. 真实 Key 不进入证据截图；
  7. 浏览器不得读取完整 Key；
  8. Local Agent 无必要时不得获得 LLM Key；
  9. 页面只显示掩码；
  10. 只有企业管理员可新增、更新、测试和撤销企业 Key；
  11. Key 使用加密 Secret 引用；
  12. 审计记录谁在何时修改配置；
  13. 任务只记录 credential configuration/version ID，不记录 Key。

  第一版领域模型可以规划 LlmProviderConfig（organizationId、provider、baseUrl、model、credentialSource: platform | organization、encryptedSecretRef、status、createdBy、updatedBy、lastConnectionTestAt）。**本轮只做文档规划，不实现 Key 存储。** 新增开放问题：Q-019（MVP 默认 LLM Provider 和模型）、Q-020（企业 BYOK 上线阶段与允许的 Provider）、Q-021（腾讯云具体基础设施选型）、Q-022（第一版企业登录方式）。
- **原因**：MVP 用平台默认凭证让普通用户零配置使用文案能力；企业 BYOK 满足后续企业自有模型诉求；安全底线防止 Key 泄露。
- **影响**：DOMAIN_MODEL 规划 LlmProviderConfig；INFORMATION_ARCHITECTURE 设置区规划「AI 模型」（平台默认模型/企业自有 API Key）；PROVIDER_AND_AGENT_ARCHITECTURE 区分 LLM Key 与 Hifly Token 两类凭证；OPEN_QUESTIONS 新增 Q-019～Q-022。
- **被否决方案**：MVP 即要求每个用户配置自己的 API Key；把领域模型绑定到 owner 私人 Key；本轮实现 Key 存储。
- **可重新评估条件**：Q-019/Q-020 决定后细化 Provider 与 BYOK 实现；「真实 Key 安全底线 + 平台默认凭证/企业 BYOK 两级模型」不重新开放。
