- Phase 2 边界：Local Agent 真实领取、Provider 自动执行与回调、自动产物回传不在本批；界面不出现「自动执行中 / Agent 心跳 / 执行器在线」等暗示已实现自动化的元素（D-030 §11、§12；D-028 §27）。

## 1. 用户工作流分析

### 1.1 进入原因与任务

| 角色 | 进入原因 | 要完成的任务 |
|---|---|---|
| 运营（兼执行者） | 交接包已下载，要正式开始人工执行 | 领取人工任务 → 核对包版本与完整性摘要 → 确认开始 |
| 运营（兼执行者） | 已按交接包在线下完成视频制作 | 上传候选产物（主要视频 + 辅助材料）→ 填写执行结果与偏差 → 提交不可变执行报告 |
| 运营 | 执行中遇到登录失效、页面验证、素材不可用等问题 | 提交 outcome=requires_action/failed 的报告，记录原因、阶段与恢复要求 |
| 运营 | 报告已提交，想知道产物是否被接受 | 查看产物核验状态；核验失败时查看原因、重新上传并提交更正报告 |
| 运营 | 日常巡检 | 扫工单列表「哪单在可领取 / 执行中 / 需要处理 / 核验中 / 已完成」 |
| 运营 / 管理员 | 计划变更 | 请求取消工单（未确认前可放弃领取）；跟踪取消确认 |
| 运营 / 审核视角成员 | 作品已登记 | 检查作品：标记可交付 或 要求返工（分类 + 原因 + 返回上游阶段） |
| 运营 | 作品可交付 | 安全下载作品；按真实交付动作登记交付记录；再次交付时登记新记录 |
| 运营 | 审计与追溯 | 查看工单执行记录、报告历史（含被更正版本）、检查历史、交付历史 |

主链路（本批终点加粗）：**工单等待执行（A09）→ 交接包可下载（A10）→ 领取人工任务（创建执行记录，≠ 开始执行）→ 确认开始（执行中）→ 上传候选产物（已上传 ≠ 核验通过）→ 提交执行报告（completed ≠ 工单完成）→ 服务端产物核验（通过 + 登记作品，同一事务）→ 工单已完成 → 作品库检查（可交付门禁）→ 登记交付（幂等，历史不可覆盖）**。

### 1.2 最高频动作（按优先级排序，决定布局与默认焦点）

1. 判断「这个工单现在到哪一步、下一步该谁做什么」（状态扫描，每屏首务）。
2. 领取任务、确认开始（每单一次，但语义最重：领取才创建执行记录，确认开始才进入执行中）。
3. 上传候选产物、提交执行报告（执行后必经）。
4. 查看核验结论与失败原因；失败后的更正报告路径。
5. 检查作品（标记可交付 / 要求返工）与登记交付。
6. 翻查执行记录、报告、检查与交付历史（低频，全部折叠/只读）。

### 1.3 最危险的误操作（按后果排序，决定确认层级与文案）

1. **把「报告执行完成」当成「工单完成」** —— 报告 outcome=completed 只推进执行记录；工单完成须服务端核验通过且作品登记成功（D-029 §13、D-030 §10.2）。界面：报告 Dialog 内固定提示 +「执行完成」badge 用信息蓝不用绿 + 旁列核验 badge 接管后续状态。
2. **把「上传完成」当成「核验通过」** —— 候选产物行 badge 严格区分「已上传 · 待提交报告 / 等待核验 / 核验中 / 核验通过 / 核验失败 / 需要人工处理」；上传成功 notice 固定含「上传完成不代表核验通过」（D-029 §14）。
3. **把「下载交接包」当成「开始执行」** —— A10 已建立的防线继续：包「可下载」badge 与执行状态 badge 永远同屏并列；只有「领取 + 确认开始」两步后才进入执行中（D-029 MHC-004）。
4. **重复点击/双击/网络重试产生重复领取、重复报告、重复交付** —— 全部命令按钮受理即禁用并携带幂等键；相同请求安全重放并提示「已受理/已登记」；真实再次交付必须再次显式打开 Dialog 发起新命令（D-029 §17 MHC-009）。
5. **把 requires_action 当成失败** —— 一律 amber「需要处理」，配原因与恢复要求；恢复动作是「完成处理并重新检查」（触发服务端真实恢复检查），不存在「标记已处理直接成功」（D-029 §13、LF-009、LF-017）。
6. **把「下载作品」当成「交付」** —— 下载按钮旁固定提示「下载不等于交付；交付请使用登记交付」；交付是显式业务命令并产生不可变交付记录（D-028 §21 DM-002）。
7. **以为更正报告会覆盖旧报告 / 重新检查会删除旧检查** —— 更正报告创建新报告版本并标注替代关系，旧报告只读保留；重新检查创建新检查记录，旧检查标记「已被新检查取代」；界面不提供任何编辑/删除历史入口（D-029 §12、D-028 §20）。
8. **未核对包版本就开始执行** —— 「确认开始执行」Dialog 强制展示工单目的、交接包版本与完整性摘要，要求执行者核对手中副本一致（D-029 §11 attempt 绑定 package_id+package_version+manifest_hash 的用户可理解投影）。
9. **以为核验失败 / 执行失败等于工单终结** —— 核验失败不创建作品、工单不完成，给出更正报告或重新上传路径；可重试技术失败可再次执行（新执行记录）；只有业务不可恢复时工单才 failed，并引导「返回视频方案 →」创建新版本与新工单（D-029 §13、§20）。
10. **单方面取消正在执行的工单** —— 取消是危险确认（Dialog + 红实心确认按钮）；已有执行中的记录时工单进入「取消中」，须执行者以 outcome=cancelled 的报告确认停止后才「已取消」（D-029 §13）。

### 1.4 与本批之外的关系

- 上游变化（文案/人物/商品快照/方案变化）不走本页：本页全部输入快照只读，引导返回对应权威阶段创建新版本、新工单（D-029 §19）。
- 全局「生产任务」页（LF-009）与跨项目工单聚合评估见 §2.4：本批不新建，理由与后续节奏明确记录。

## 2. 页面信息架构

### 2.1 结论：A11/A12 增量复用 production.html；A13 新建作品库 works.html；本批不建全局生产任务页

| Slice | 页面归属 | 形式 | 理由 |
|---|---|---|---|
| A11 人工执行与结果回传 | `production.html`（阶段 5 工作台） | 增量：右栏「人工执行」面板替换 A10 的禁用占位卡；新增确认开始 Dialog、执行报告 Dialog；中栏增加取消工单入口 | 领取/开始/上传/报告都绑定具体工单上下文，「异常与操作就近」；A09-A10 已把 A11 入口锚定在右栏视线终点，用户心智已建立 |
| A12 产物核验与作品创建 | `production.html` | 增量：候选产物行核验 badge、核验摘要条、工单完成态、作品结果卡 | 核验对象是「该工单的候选产物」，拆开会造成高频跨页跳转；工单完成与作品登记必须在工单上下文同屏可见（MHC-007 的用户投影） |
| A13 作品检查与交付 | **新页面 `works.html`（作品库）** | 一级导航真实入口（feature flag 控制，未开放不进导航） | LF-010 定义作品库为一级导航对象库：作品是一等全局对象，需稳定详情入口（LF §3）；「生产中的候选文件和核验失败记录继续留在生产任务中，作品库只接收正式作品」——检查/交付塞进单商品工作台会混淆候选与正式作品的边界 |
| 全局「生产任务」页（LF-009） | 本批不建 | A14 / Stage 3 再评估 | 见 §2.4 |

为什么 A11/A12 不新建页面：

1. 对象是同一工单的延续状态链（等待执行 → 执行中 → 核验 → 完成），A09-A10 的「左列表 / 中详情 / 右决策」三栏心智直接延伸，运营零学习成本。
2. 「包已下载 ≠ 已开始执行 ≠ 核验通过 ≠ 工单完成」的防误操作设计依赖多类 badge 同屏并列；拆页会削弱 §1.3。
3. 移动端已有「工单抽屉 + 单栏堆叠 + 吸底主操作」模式，增量面板自然落入同一滚动流。

为什么 A13 确需新页面：作品跨商品、跨项目被浏览与交付；交付往往按项目/批次进行而非单工单上下文；LF-010 将预览、检查、交付登记、来源查看定义为作品库职责。works.html 不是平行产品——它是作品（A12 产物）的权威归属页，production.html 作品卡只做摘要与跳转。

### 2.4 导航与全局页评估

- 一级导航在 A13 落地且 `worksEnabled` 开启后新增「作品库」入口，顺序：项目 / 素材中心 / **作品库** / 成员管理（沿用 shell.js 的 `data-feature` 模式；开关关闭时入口不出现，不做灰显假入口）。
- 「生产任务」全局页本批不建，理由：① Phase 1 人工链路的异常量级低，requires_action/失败/核验异常均可在工单页就地发现与处理，LF-009 的核心管理能力（异常处理、attempt 历史、核验状态）已被 production.html 覆盖；② 再建全局列表会与 production.html 形成平行重复产品，违反「不凭空建立重复的平行产品」；③ A14 负责跨页面导航与端到端加固，跨项目聚合视图在 A14/Stage 3 以真实使用数据评估后再设计，本批不预留 UI 元素。跨项目发现的效率缺口记录为后续项（见 §12 D4）。
- plan/copy/avatar 等上游页面零改动；阶段条不变。

### 2.5 对象组织

| 对象 | 位置 | 组织方式 |
|---|---|---|
| 工单 | production.html 左栏 | 双行行：目的中文名 + 状态 badge 一行；创建时间 + 执行/核验/作品摘要点一行；选中行 tint-bg + 左 3px 品牌边（现状样式延续） |
| 执行记录（attempt） | 右栏人工执行面板 + 执行记录折叠区 | 当前一次执行为状态卡；历史每次执行一行（第 N 次执行 · badge · 领取人 · 起止时间），展开可见报告版本 |
| 执行报告 | 报告 Dialog（提交）+ 执行记录内只读卡（查看） | 不可变；更正版本标注「更正自 v(N-1)」，被更正版本标注「已被 v(N+1) 更正」 |

## 5. 状态设计

颜色语义严格映射 `tokens.css`：成功绿（success）、提醒 amber（warning）、失败红（danger）、失效灰（inactive 纯灰）、进行中/等待信息蓝（progress）。红只给真实失败与危险确认；requires_action、等待、阻断、离线提醒一律不用红（Stage 0 §5.4 红线）。badge 只复用既有语义类，不新增色值。

### 5.1 ProductionOrder 工单全生命周期（D-028 §15；A09-A10 只投影前三态，本批起全量出现）

| 状态 | 中文文案 | 颜色语义 | 下一步操作 |
|---|---|---|---|
| `draft` | 草稿（过渡投影） | 中性灰 | 无操作；随即固定快照 |
| `ready` | 已就绪（过渡投影） | 信息蓝 | 随即转入等待执行 |
| `waiting_for_executor` | 等待执行 | 信息蓝 | 生成/下载交接包；领取人工任务 |
| `claimed` | 已领取 · 待确认开始 | 信息蓝 | 确认开始执行 / 放弃领取 |
| `running` | 执行中 | 信息蓝 | 上传候选产物；提交执行报告 |
| `requires_action` | 需要处理 | **提醒 amber，不得用红** | 查看原因与恢复要求；完成处理并重新检查；更正报告 |
| `succeeded` | 已完成 | 成功绿 | 前往作品库检查与交付 |
| `failed` | 失败 | 失败红 + 业务原因 | 返回对应上游阶段创建新版本、新工单；历史保留 |
| `cancel_requested` | 取消中 | 提醒 amber | 等待执行者以「确认停止执行」报告确认；不可新操作 |
| `cancelled` | 已取消 | 失效灰 | 只读查看；如需生产走新工单 |

未知/异常状态值：中性灰「状态待确认」+ 手动刷新，不归入失败或成功（沿用 A09-A10 规则）。

### 5.2 执行（ExecutionAttempt）状态（D-028 §16 权威集合 + 1 个界面投影）

| 状态 | 中文文案 | 颜色语义 | 下一步操作 |
|---|---|---|---|
| `available`（**界面投影，非领域状态**） | 可领取 | 信息蓝 | 【领取人工任务】；投影条件 = 工单等待执行 + 交接包可下载 + 无有效运行中的执行 + 有权限 |
| `created` | 已创建（过渡投影） | 信息蓝 | 领取与创建在同一命令内完成，正常不可见；若可见按「已领取」处理 |
| `claimed` | 已领取 · 待确认开始 | 信息蓝 | 【确认开始执行】/【放弃领取】 |
| `running` | 执行中 | 信息蓝 | 上传候选产物；【提交执行报告】 |
| `requires_action` | 需要处理 | **提醒 amber** | 显示原因 + 恢复要求 + 责任角色；【完成处理并重新检查】触发真实恢复检查；之后可更正报告继续 |
| `succeeded` | 执行完成 | 信息蓝（**不用绿**，避免与工单完成混淆） | 等待产物核验；文案固定「执行完成不等于工单完成」 |
| `failed` | 执行失败 | 失败红 + 错误分类业务文案 | 可重试技术问题 →【重新领取任务】（新执行记录）；业务/输入问题 → 返回上游新工单 |
| `cancel_requested` | 取消中 | 提醒 amber | 执行者以 outcome=cancelled 报告确认停止 |
| `cancelled` | 已取消 | 失效灰 | 只读保留 |
| `timed_out` | 领取已过期 | 失效灰 | 任务回到可领取；任何人可重新领取 |
| `superseded` | 已被新执行替代 | 失效灰 | 只读保留（重试/换人产生新执行记录时旧记录不删除） |

### 5.3 执行报告（ManualExecutionReport）outcome 与修正（D-029 §12 权威枚举）

| outcome | 中文文案 | 颜色语义 | 界面说明与下一步 |
|---|---|---|---|
| `draft`（**界面投影，非领域状态**） | 填写中（未提交） | — | 报告 Dialog 内本地状态；**不落库**，关闭或刷新即丢失；Dialog 有输入时关闭需确认；不存在服务端报告草稿（见 §12 D1） |
| `completed` | 执行完成 | 信息蓝 | 固定提示「执行完成不等于工单完成；核验通过并登记作品后工单才完成」；进入产物核验 |
| `requires_action` | 需要处理 | 提醒 amber | 必填原因与恢复要求；不等于失败；恢复需真实重新检查 |
| `failed` | 执行失败 | 失败红 | 必填错误分类（可重试技术问题 / 输入或业务问题 / 无法判断）与失败阶段；工单走向由服务端按类别决定 |
| `cancelled` | 已确认停止 | 失效灰 | 仅在工单「取消中」时可选择，配合取消请求；执行者不得单方面取消工单（D-029 §13） |

修正规则投影：报告不可变；【提交更正报告】创建新报告版本（标注「更正自 vN」），旧报告标注「已被 v(N+1) 更正」并只读保留；同一 report_id + 相同内容的重复提交返回原结果并提示「该报告已提交」，相同 report_id + 不同内容被服务端拒绝并按冲突流程提示（界面不预填冲突细节，只引导刷新后核对）。作品登记后更正入口禁用：「作品已按原报告登记，如需变更请走返工流程」。

### 5.4 候选产物与产物核验状态（A12；核验业务投影命名，见 §12 D2）

候选产物自身状态（上传后、报告提交前）：`已上传 · 待提交报告`（信息蓝）。核验在报告 outcome=completed 后由服务端启动；候选行 badge 与面板摘要条共用以下投影：

| 核验投影 | 中文文案 | 颜色语义 | 下一步操作 |
|---|---|---|---|
| `queued` | 等待核验 | 信息蓝 | 等待；可离开本页 |
| `running` | 核验中 | 信息蓝 | 等待；轮询恢复；无百分比、无假进度 |
| `passed` | 核验通过 | 成功绿 | 等待作品登记结果（与工单完成同一事务投影） |
| `failed` | 核验失败 | 失败红 + 业务化原因（如「文件内容与登记摘要不一致」「文件类型不符合输出要求」「数量不符合主要产物要求」） | 重新上传产物并提交更正报告；不创建作品、工单不完成 |
| `requires_action` | 需要人工处理 | **提醒 amber** | 显示原因与处理要求；处理后重新检查；不得「标记已处理」直接通过 |
| 核验任务技术失败（技术投影，非业务结论） | 核验未完成 | 失败红 + 脱敏原因 | 【重新核验】（幂等，不重复创建作品）；与业务核验失败分开表达（类比 QualityRun / QualityResult 分离） |
| 核验任务进行中提示 | 「产物核验中，可离开本页，状态自动更新」 | 面板摘要条，信息蓝 | 轮询 + 手动刷新 |

工单级合成投影：核验通过 + 作品登记成功 → 工单「已完成」绿 + 作品结果卡；核验通过但作品登记技术失败（同事务回滚投影）→「登记未完成（技术原因）」红 +【重试登记】（幂等键不变，不重复创建作品）；**任何情况下一工单最多一个主要视频作品**：已有作品后上传区与报告入口关闭，说明「本工单已登记正式作品」（MHC-006）。

### 5.5 作品 / 检查 / 交付状态（D-028 §19–§21、LF-010）

作品（Work 生命周期）：

| 状态 | 中文文案 | 颜色语义 | 下一步 |
|---|---|---|---|
| `available` | 正常 | 中性灰（不喧宾夺主，交付状态承担主语义） | 检查 / 下载 / 交付 |
| `unavailable` | 暂不可用 | 失效灰 + 原因 | 操作禁用；联系管理员 |
| `withdrawn` | 已撤回 | 失效灰 + 原因 | 操作禁用；历史保留 |

检查（WorkInspection，权威四态）：

| 状态 | 中文文案 | 颜色语义 | 下一步 |
|---|---|---|---|
| `pending` | 待检查 | 信息蓝 | 【标记可交付】/【要求返工】 |
| `passed` | 可交付 | 成功绿 | 【登记交付】解锁 |
| `rework_required` | 需要返工 | **提醒 amber，不用红** | 按返回阶段指引回上游；原作品与历史保留 |
| `superseded` | 已被新检查取代 | 失效灰 | 历史折叠区只读 |

交付（DeliveryRecord 是事件不是状态；页面交付状态为计算投影）：

| 投影 | 中文文案 | 颜色语义 | 计算依据 |
|---|---|---|---|
| 待交付 | 待交付 | 信息蓝 | 检查可交付 且 无交付记录 |
| 已交付 | 已交付 · 共 N 次 | 成功绿 | 存在 ≥1 条有效交付记录（DM-002） |
| （交付记录本身） | 逐行：时间 · 交付人 · 方式 · 备注 | 中性文本，无 badge | 追加式只读；重复网络请求不产生新记录 |

### 5.6 命令级与页面级通用异常（两页通用）

| 状态 | 中文文案 | 呈现 | 下一步 |
|---|---|---|---|
| `no_permission`（forbidden） | 「你可以查看，但没有 <操作> 权限；请联系管理员或有权限的成员处理」 | amber blocked notice + 按钮禁用带原因 | 联系管理员；不出现 403/RBAC 字样 |
| 未认证（unauthorized） | — | 跳转登录页（现有 request 封装行为） | 重新登录后回到原 URL |
| `version_conflict` / 409 | 「页面内容已过期，请刷新后继续」 | amber notice + [刷新] | 刷新后重新确认；不静默覆盖他人操作 |
| `technical_failure` | 「<操作> 未完成（技术原因），你的操作未生效」 | 红色 error notice + [重试] | 相同幂等键安全重试 |
| 业务阻断 `business_blocked` | 逐条原因 + 影响对象 + 返回权威页链接 | amber blocked notice + 按钮禁用 | 按指引返回权威阶段 |
| 跨组织/非法 ID | 「此对象不在本企业可用范围内」 | amber blocked notice | 返回项目内权威页面；不显示内部 ID |
| 幂等安全重放 | 「请求已受理 / 该报告已提交 / 该交付已登记」 | 信息蓝/成功 notice + 定位到首次结果 | 在首次结果上继续 |
| 加载中 / 空 / 加载失败 | 骨架行；三分类空状态；error notice + [重试] | 沿用 base.css 模式 | — |
| 异步恢复 | 核验中/上传中离开再回来 | 状态全部由服务端重建；轮询 + 手动刷新 | 无假进度条 |

### 5.7 必须保持的关键区分（设计与文案双重保证）

1. 生成/下载交接包 ≠ 创建执行记录；领取 + 确认开始才进入执行中（MHC-004）。
2. 上传完成 ≠ 核验通过；候选产物 ≠ 正式作品（MHC-006/007）。
3. 报告 completed ≠ 工单完成；执行完成（attempt succeeded）≠ 工单完成（order succeeded）（D-028 §16、D-029 §13）。
4. 只有核验通过且作品登记成功（同一事务）工单才「已完成」（MHC-007、D-028 §26）。
5. 下载作品 ≠ 交付；交付是显式命令产生的不可变记录；重复网络请求不产生重复交付记录（DM-002、D-029 §17）。
6. requires_action ≠ failed（amber）；waiting_for_executor ≠ failed（信息蓝）。
7. 报告、检查、交付记录不可变：更正 = 新报告版本；重新检查 = 新检查记录；再次交付 = 新交付记录；旧记录全部只读保留。
8. 「状态待确认 / 填写中 / 可领取 / 待交付 / 已交付 · 共 N 次」为界面投影文案，不发明领域状态；全部映射 D-028 §15–§21 与 D-029 §12–§14。

## 7. 交互设计

### 7.1 领取人工任务（A11）

- 门禁（服务端重验）：工单 `waiting_for_executor` + 交接包 `ready` + 无有效运行中的执行 + 当前成员有权限；包 `revoked` 禁止领取；包 `expired` 先引导重新获取下载权限回到 `ready` 再领取（门禁原因就地 amber 列出）。
- 点击 → 受理即禁用（loading）→ 成功：状态卡「已领取 · 待确认开始」+ success notice「已领取；确认开始后进入执行中」；幂等：同一领取请求重复提交返回同一执行记录 +「已为你恢复本次领取」；他人已领取：amber「本任务已由 <姓名> 领取」+ 操作禁用。
- 领取不启动执行：不显示「执行中」直到确认开始。

### 7.2 确认开始执行（A11）

- Dialog（§3.2）：工单目的 + 包版本 + 完整性摘要 + 核对提示；【确认开始执行】受理即禁用；成功后工单与执行记录进入「执行中」，上传区开放。
- 打开 Dialog 时与提交时均由服务端重验（工单/包/权限/无其他运行执行）；包版本已被替代或停用时拒绝并 amber 提示刷新。

### 7.3 上传候选产物（A11）

- 入口仅在「执行中」开放；复用素材中心的一行式文件输入；主要产物限 1 个槽位，已有候选时需先【移除】再上传（已随报告提交的主要候选不可移除）；辅助材料多个。
- 流程：选择文件 → 上传中行 badge「上传中」（信息蓝）+ 按钮 loading → 成功行 badge「已上传 · 待提交报告」+ notice「上传完成不代表核验通过；核验在提交执行报告后进行」；失败红色 error notice（脱敏业务原因）+ 可重选重传；同一文件重复上传幂等返回原候选 +「该文件已上传」。
- 上传中断/刷新：已上传候选从服务端恢复；未完成的浏览器传输需重新选择文件（不伪装断点续传）。

### 7.4 提交执行报告（A11）

- 【提交执行报告】在无主要产物且选择「执行完成」时禁用并提示「执行完成需要至少上传主要产物」；outcome 无默认选中。
- 提交：受理即禁用 + 幂等键；成功：报告只读卡进入执行记录，attempt 按 outcome 投影；completed → 自动进入核验序列（A12 未开放时显示「产物核验将在后续阶段开放」禁用说明）。
- Dialog 固定文案：「提交后报告不可修改；如需更正请提交更正报告，原报告保留。」

### 7.5 偏差记录（A11，报告表单内）

- 复选项（§3.4）：默认勾「无偏差」；勾选任一真实偏差时「无偏差」自动取消且偏差说明必填。
- 「执行环境自动修改了文案内容」属核心输入偏差：勾选就地 amber「核心输入偏差不会自动登记作品，需人工判断」（D-029 §12），不阻止提交。
- 偏差内容进入报告与执行记录只读展示；不允许事后编辑。

### 7.6 requires_action 恢复（A11/A12）

- 展示：amber 卡 = 原因 + 恢复要求 + 责任角色 + 记录时间。
- 恢复动作【完成处理并重新检查】：触发服务端真实恢复检查（异步），按钮 loading，结果投影：通过 → 回到「执行中」可继续（更正报告追加产物）；未通过 → 保持需要处理 + 更新原因。**不存在「标记已处理」直通成功**。
- 核验侧 requires_action 同理：处理入口 + 重新检查；人工判断结论由服务端记录。

### 7.7 放弃领取与取消工单（A11）

- 放弃领取：次按钮 + 小确认 Dialog（对象 + 后果「任务回到可领取，本次执行记录标记已取消」）；仅「已领取 · 待确认开始」可用；命令语义由 Issue #67 固化（见 §12 D10）。
- 取消工单：中栏底部 [取消工单] 危险按钮（白底红字），仅非终态可见；Dialog 写明对象与后果、确认按钮红实心「确认取消工单」。无运行执行 → 工单「已取消」；有执行中 → 工单「取消中」，执行者报告 Dialog 出现「确认停止执行」选项，确认后「已取消」；取消不删除任何历史。

### 7.8 更正报告（A11/A12）

- 入口：执行记录内报告卡 [提交更正报告]；核验失败/需要处理时面板操作区同步出现。
- Dialog 与报告表单同构，额外标注「更正自 vN」、允许追加/替换候选产物引用；提交产生新报告版本；旧版本只读保留。
- 幂等：同一更正请求重复提交返回同一新版本；作品已登记后入口禁用（§5.3）。

### 7.9 核验与重试（A12）

- 自动开始：报告 completed 提交后；queued/running 轮询（沿用 A10 的 2.5s 间隔模式，终态停止）+ 手动刷新。
- 技术失败：【重新核验】幂等重试；业务失败：更正报告路径；requires_action：§7.6。
- 核验通过 + 作品登记：工单 badge「已完成」、作品结果卡出现、上传/报告入口关闭；登记技术失败：【重试登记】（幂等，不重复创建作品）；同一工单已存在主要视频作品时服务端拒绝并提示已存在（界面显示既有作品卡）。

### 7.10 作品检查（A13）

- 【标记可交付】：确认 Dialog（作品摘要 +「确认此作品通过检查，可交付」）→ 新检查记录（可交付）。
- 【要求返工】：表单 Dialog = 分类下拉（内容不符合方案 / 画面质量 / 声音或人物表现 / 文件或格式 / 其他）+ 原因（必填）+ 返回上游阶段下拉（视频方案 / 文案与质检 / 人物与素材 / 商品与目标）+ 说明「原作品与检查历史保留；返工需在对应阶段创建新版本并创建新工单」→ 新检查记录（需要返工）+ 作品卡给「前往 <对应阶段> →」链接。不自动创建新工单（A09 的返工目的由用户在创建新工单时显式选择）。
- 再次检查：两个命令随时可对同一作品再次执行，创建新检查记录，旧记录标「已被新检查取代」只读保留。

### 7.11 交付登记与重复交付（A13）

- 门禁：当前有效检查 = 可交付 且 作品正常；否则【登记交付】禁用并说明（待检查 →「先完成检查」；需要返工 →「需要返工」）。
- 【登记交付】Dialog：交付方式下拉（线下转交 / 邮件 / 企业网盘 / 其他）+ 备注（可选）+ 交付时间（默认现在，可改）+【确认登记交付】；受理即禁用 + 幂等键。
- 成功：success notice「已登记交付」+ 交付历史插入一行 + 交付状态变「已交付 · 共 N 次」。
- 重复网络请求/双击/刷新重提交：返回首次记录 +「该交付已登记」，不产生新事件；真实再次交付：再次显式打开 Dialog 提交新命令 → 新记录；历史永不覆盖、无编辑/删除入口。
- 【下载作品】：短时授权下载（不暴露永久地址），旁注「下载不等于交付；交付请使用登记交付」；下载可重复、不产生任何业务记录。

### 7.12 危险操作与 Dialog 使用（低打扰原则）

| 操作 | 是否 Dialog | 确认强度 |
|---|---|---|
| 领取 / 放弃领取 | 否 / 是（小确认） | 可逆 |
| 确认开始执行 | 是 | 包版本 + 完整性摘要核对（语义最重的人工确认点） |
| 提交/更正执行报告 | 是（表单即确认） | 不可变提示；提交按钮为最终确认 |
| 取消工单 | 是 | 写明对象与后果，红实心确认 |
| 移除候选产物（未进报告） | 否 | 就地反馈 |
| 标记可交付 | 是（轻确认） | 作品摘要 + 结论 |
| 要求返工 | 是（表单即确认） | 必填原因与返回阶段 |
| 登记交付 | 是（表单即确认） | 幂等提示；历史不可覆盖 |
| 下载交接包 / 下载作品 | 否 | 固定提示文案 |

### 7.13 刷新 / 离开 / 重进

- 所有状态从服务端恢复；上传中/核验中离开再回来状态完整；轮询终态停止。
- 报告 Dialog 有未提交输入：关闭 Dialog 需确认；刷新页面本地输入丢失（Dialog 内固定提示「未提交的报告内容不会保存」）。
- 工单/商品/作品切换：无本地输入（除 Dialog），无需离开保护。

### 7.14 终态边界

前端只发业务命令（领取/确认开始/放弃/上传完成回调/提交报告/更正报告/重新检查/取消工单/重新核验/重试登记/标记可交付/要求返工/登记交付），**永不直接写 succeeded/passed/available 等终态**；badge 全部来自服务端响应；异步进行中只有「等待」投影，不做乐观完成。

## 8. 动效设计

沿用既有 token（`--motion-fast: 140ms`、`--motion-panel: 220ms`、`--ease-out`），120–240ms、ease-out、无弹簧/回弹/循环。

| 场景 | 动效 | 时长 |
|---|---|---|
| 命令成功/失败 notice 出现 | opacity 淡入（既有 `notice-in`） | 150ms |
| badge 状态变化（可领取→已领取→执行中；已上传→核验中→核验通过/失败；待检查→可交付） | 颜色 cross-fade | 120ms |
| 候选行/交付历史行/检查历史行插入 | 单次淡入，无位移弹跳 | 140ms |
| 全部 Dialog 与移动端抽屉 | opacity + translateY(8px→0)（既有 `dialog-in`） | 200–220ms |
| 选中行、折叠区展开 | 背景/边框色过渡 | 120–150ms |
| 上传中/核验中 | badge 静态文案 + 按钮 spinner（仅 spinner 旋转，线性） | — |
| 骨架加载 | 静态灰条或单次淡入 | — |

明确禁止：虚假进度条与百分比；循环呼吸/脉冲；数字滚动；位移引起的布局跳动；任何 > 240ms 动效；把等待动画当成功证据。

**prefers-reduced-motion**：沿用 base.css 既有 media query；本批补充——Dialog/抽屉瞬时显隐；上传中/核验中以静态 badge + 文案表达；骨架不闪烁；状态信息永不单独依赖动效传达（颜色 + 文字双编码）。

## 12. DESIGN_BLOCKER 与已记录决策

### 12.1 结论

**未发现 DESIGN_BLOCKER。** Issue #67/#68/#69、D-028 §15–§21、D-029 §11–§17、LF-008/LF-009/LF-010 与本设计在状态机、门禁、幂等、不可变性与安全边界上一致；本设计不修改任何领域状态定义，不把 QC passed 当 approved，不由前端模拟服务端终态。
