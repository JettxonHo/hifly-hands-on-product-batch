# Kimi K3 前端视觉升级计划

> 状态：Design and orchestration plan only
> Owner：JettxonHo
> 创建日期：2026-08-06
> Stage 0 视觉方向：Owner 已于 2026-08-06 批准
> 适用范围：Vertical Slice A 的业务前端
> 非目标：本文件不授权修改代码、创建 PR、合并、访问 Hifly 或消耗积分

## 1. 目标

在不改变领域规则、权限、API、数据库和状态机的前提下，把当前功能验收型页面升级为适合企业运营人员长期使用的统一工作台。

升级后的界面应当：

- 安静、清晰、适合高频操作和信息扫描；
- 统一 A01-A14 的导航、页面结构、表单、列表、状态和反馈；
- 让业务状态、阻断原因和下一步操作容易理解；
- 使用克制且有意义的动效表达保存、上传、异步任务和状态变化；
- 保持桌面端高效率，并在窄屏设备上不溢出、不遮挡、不丢失关键操作；
- 保留现有业务行为和自动测试，不把视觉重构变成业务重写。

## 2. 协作角色

| 角色 | 职责 |

| Owner | 批准视觉方向、阶段范围与最终验收，不负责技术细节 |
| Claude Stage 0 Orchestrator | 只负责读取仓库规范、协调 Kimi K3、复核业务边界和整理设计证据，不负责正式代码实施 |
| Kimi K3 Visual Designer | 只负责视觉审计、设计系统、页面布局、响应式与动效方案，不直接修改生产代码 |
| Codex Implementation Agent | 在 Owner 单独批准 Stage 1 后负责前端代码实现、测试、Git 交付和修复 |
| Independent Reviewer | 复核业务回归、可访问性、跨尺寸表现和视觉一致性，不批准自己的实现 |

Claude 必须记录 Kimi K3 的实际运行时模型。如果无法确认，应写 `UNVERIFIED_RUNTIME_MODEL`，不得用角色名假装模型已经启用；Kimi K3 不可用时不得静默换模型继续实现。

## 3. 启动条件

正式改前端代码前必须满足：

1. A01-A03 一键本地演示环境已合并到 `main`，或存在等价且可重复的 PostgreSQL 验收环境；
2. 从最新 `origin/main` 创建独立 Issue、worktree、分支和主 PR；
3. Owner 已看过 Kimi K3 产出的视觉方向稿并明确批准实施；
4. 已固定本轮允许修改的页面和文件；
5. 不与正在开发同一页面的 VSA Issue 并行写相同文件。

## 4. 实施节奏

### Stage 0：视觉审计与方向确认

只读现有页面、CSS、产品规范和状态合同，形成：

- 当前页面问题清单；
- 视觉原则、色彩、字体、间距、层级和动效方向；
- A01-A03 关键页面的桌面与窄屏静态方向稿；
- 保留、替换和禁止改动的 DOM/API 清单；
- 预计文件范围和回归风险。

本阶段结束后必须等待 Owner 批准，不直接进入代码实现。

### Stage 1：统一基础层

建立可复用但不过度抽象的基础层：

- 全局应用壳层：左侧导航、顶部上下文栏、页面标题和主操作；实施时只显示已有真实功能的目的地，未实现的未来入口只存在于 Stage 0 静态 IA 稿中；
- 设计变量：中性色、品牌强调色、语义色、排版、间距、边框和阴影；
- 基础控件：按钮、输入框、选择器、文本域、表格、标签页、状态标记、空状态、提示和对话框；
- 统一反馈：未保存、保存中、已保存、保存失败、加载失败、权限不足和版本冲突；
- 动效基础：时长、缓动、进入/退出规则和 `prefers-reduced-motion` 降级。

先覆盖 A01-A03 已实现页面，建立后续 VSA 页面遵循的视觉基线。

### Stage 2：随 A04-A14 增量落地

后续每个 VSA Issue 的业务实现继续由该 Issue 的实施 Agent 负责；Codex 根据已批准的 Kimi K3 设计方案完成视觉对齐。需要补充设计判断时，可让 Kimi K3 提供设计建议，但 Kimi K3 不直接修改生产代码。不得为了追求统一而提前创建尚未实现的空页面或伪状态。

### Stage 3：Vertical Slice A 全链路收尾

A01-A14 功能闭环后，统一检查：

- 六个一级导航与项目五阶段工作台；
- 页面间的标题、间距、主操作和返回路径；
- 正常、空、加载、失败、权限不足、冲突和失效状态；
- 跨页面动效节奏；
- 桌面、平板和窄屏适配；
- 中文长文本、长 SKU、长项目名和错误文案是否溢出；
- 键盘焦点、对比度和 reduced-motion。

## 5. 视觉方向

Stage 0 审计结果见 `docs/frontend/KIMI_K3_STAGE0_VISUAL_AUDIT.md`。Owner 已批准采用“冷中性灰 + 品牌蓝 `#1769e0`”作为统一方向；后续实施不再重新选择主视觉方案。

### 产品气质

- 企业内容生产工作台，而不是营销落地页；
- 信息密度适中，优先扫描、比较和重复操作；
- 使用中性背景、清晰层级和少量品牌强调色，避免单一紫蓝、深蓝或米色主导；
- 页面区段以无边框布局或全宽工作区组织，卡片只用于确实独立的对象、弹窗和重复条目；
- 卡片圆角不超过 8px，避免卡片套卡片；
- 不使用装饰性光球、渐变球、模糊背景或大面积营销式 Hero；
- 不用夸张大字占据运营页面；标题尺寸服从工具界面的信息密度。

### 交互和图标

- 熟悉的工具操作优先使用图标按钮，并提供 tooltip；
- 颜色选择使用色块，模式选择使用分段控件，二元设置使用开关或复选框；
- 仅明确命令使用文字按钮；危险操作与主要生产操作保持清晰距离；
- 不在普通运营页面暴露 Provider、Playwright、影刀、Token、Cookie、内部任务编号或完整本地路径。

### 动效

动效目标是简约、高级、丝滑，但必须服务于状态理解，不用于装饰：

- 控件反馈：约 120-180ms；
- 面板、抽屉和状态切换：约 180-240ms；
- 保存成功、上传完成和任务状态变化可使用轻量过渡；
- 不使用虚假进度条，不把等待动画当作成功证据；
- 不使用持续漂浮、循环呼吸或大幅位移动画；
- `prefers-reduced-motion` 下关闭非必要动画；
- 动态内容不得引发布局跳动、遮挡或按钮尺寸变化。
- 统一使用克制的 ease-out 节奏，避免弹簧、回弹、呼吸、视差和持续循环；“丝滑”来自稳定布局、连续状态和一致时长，不来自增加动画数量。

## 6. 页面优先级

### 第一批：已实现且可真实验收

1. 登录与首次改密；
2. 项目列表；
3. 项目商品工作台；
4. 素材中心；
5. 成员管理。

### 第二批：随 VSA 开发接入

1. 文案与质检；
2. 人物与素材；
3. 视频方案；
4. 生产任务与人工交接；
5. 作品库与交付记录。

不得为了视觉展示伪造尚未实现的后端能力、成功状态或生产数据。

## 7. 不可破坏的合同

- 不改变 A01-A14 的领域对象、状态机、权限和 Organization 隔离；
- 不让前端直接写 `approved`、`passed`、`succeeded`、`online` 或其他服务端终态；
- 保留 API 请求、错误码、表单字段语义、数据持久化和审计行为；
- 不删除测试依赖的可访问名称、控件角色、表单标签和稳定 DOM hook；确需变更时先更新合同测试并说明原因；
- 不改变 `npm run gui`、Playwright 兼容路径和 Capture HTTP 默认关闭边界；
- 不访问 Hifly，不运行真实生成，不消耗积分；
- 不新增前端框架、构建系统或大型依赖，除非 Owner 单独批准；
- 不提交登录态、`.local/`、数据库凭据、上传素材、截图、视频或其他运行产物。

## 8. 验收标准

每个实施 PR 应按实际改动页面、共享组件和风险选择适用验收项，不机械覆盖无关状态或视口。最低要求为：

1. 本轮目标页面的业务流程与改造前一致；
2. `npm run check` 和相关自动测试通过；
3. 使用可重复的本地数据走通受影响的关键路径；
4. 对受影响的布局选择有代表性的桌面和窄屏视口，确认无重叠、裁切或横向失控；共享布局改动再扩展到平板和宽屏；
5. 只验证受改动组件实际涉及的正常、空、加载、失败、禁用、权限不足、冲突或失效状态；
6. 受影响控件保持键盘可操作、焦点清晰，新增动效支持 reduced-motion；
7. 对可能承载长内容的受影响容器验证中文、项目名、SKU 或错误文案不会撑坏布局；
8. Independent Reviewer 给出 `APPROVED` 后，才可请求 Owner 合并。

视觉截图和报告保存在 Git 忽略目录，只在 PR 描述中引用必要的脱敏证据，不提交运行截图到仓库。

## 9. Git 与任务边界

- Stage 0 只能提出候选 Frontend Foundation Enabler，不能自行创建或开始实施；只有它确实跨多个 Slice 复用，并经 Owner 单独建立/授权 Issue 与任务合同后，才可成为独立任务；
- 获批任务必须限定已有页面、用户结果、文件和回归范围，不能把全量视觉重构打包进一个基础 PR，也不能塞进 A04；
- 一个 Issue 原则对应一个分支、一个主 PR；
- 实施者不得批准或合并自己的 PR；
- 未经 Owner 明确授权，不 merge、不关闭 Issue、不开始下一阶段；
- 本计划本身只授权规划和交接，不构成任何代码实施授权。

## 10. 已知风险

1. 过早重写全部页面会与 A04-A14 功能开发冲突，因此只先建立基础层和已完成页面基线；
2. 当前页面使用原生 HTML/CSS/JavaScript，视觉升级应优先沿用，不借机迁移框架；
3. 过度动画会降低运营效率，动效必须由状态变化触发；
4. Kimi K3 输出仍需 Claude 和独立 Reviewer 校验，不能以模型名称替代代码审查；
5. A01-A03 一键演示环境尚未进入 `main` 时，不应让视觉实现建立在未合并分支上。
