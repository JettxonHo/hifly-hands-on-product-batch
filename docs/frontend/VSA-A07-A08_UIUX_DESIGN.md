## 1. 用户工作流分析

### 1.1 进入原因与任务

| 角色 | 进入原因 | 要完成的任务 |
|---|---|---|
| 运营 | 文案已批准，需要选定出镜人物 | 浏览人物目录 → 核对授权与能力 → 显式确认人物选择 |
| 运营 | 人物授权到期 / 业务调整 | 更换人物（确认新人物，旧选择保留为历史） |
| 运营 | 文案 + 人物就绪 | 创建视频方案 → 填写输出说明 → 保存 → 运行预检 → 处理阻断/提醒 → 提交方案审核 |
| 运营 | 方案被打回 / 上游变化导致失效 | 查看意见或失效原因 → 返回上游权威阶段处理 → 创建新方案版本 → 重新预检 → 重新提交 |
| 运营 | 日常巡检 | 扫多商品的「人物是否已确认」「方案到哪一步」 |
| 审核人 | 有 pending 方案审核 | 对照上游摘要（商品/文案/人物）、预检三组结论 → 批准或要求修改（必填意见） |

主链路（单商品）：**人物与素材（浏览 → 显式确认 → AvatarSelection confirmed）→ 视频方案（创建方案版本 → 输出说明 draft → 预检 → frozen → 提交审核 → 人工批准）→ 生成与交付（A09，本批只给禁用说明）**。

### 1.2 最高频动作（按优先级排序，决定布局与默认焦点）

1. 扫人物列表，判断「谁能用、谁不能用、为什么」（业务可用状态 + 授权状态双 badge）。
2. 核对当前人物选择是否仍然有效（授权到期、上游批准失效）。
3. 确认 / 更换人物。
4. 看方案版本的预检三组结论，找到阻断项并返回上游处理。
5. 审核人批准 / 要求修改。
6. 切换商品继续处理下一件。

### 1.3 最危险的误操作（按后果排序，决定确认层级与禁用策略)

1. **把「人物存在」当成「人物可用」** —— 授权已失效 / 信息不完整 / 能力未验证的人物，确认按钮禁用并逐条说明原因；已失效授权不得用于新方案（Issue #63 验收场景）。
2. **把无 Evidence 的能力当成已支持** —— 能力摘要只列已验证项；未验证项灰色标注「未验证」，不进入任何「支持」语义；不得因人物存在而宣称支持任意声音、背景、商品、比例、时长（LF-006）。
3. **把 Preflight passed 当成方案已批准** —— 预检 badge 与审核 badge 永远并列；「提交方案审核」按钮与确认文案均含「人工审核」字样；approved 只来自人工操作（LF-007、DM §13）。
4. **把 Local Agent 离线当成失败/阻断** —— 它只是生产准备度提醒：不红、不阻止保存/预检/审核，文案明确「不影响方案审核」（Issue #64 验收场景）。
5. **更换人物后以为旧方案继续有效** —— 更换确认对话框明确后果「已创建的视频方案需重新确认，将产生新方案版本」；旧选择与旧方案历史全部保留（DM §11、LF-006）。
6. **用历史批准套用过期上游** —— 上游变化后预检 invalidated、批准 revoked 均以 amber 阻断条呈现，revoked 不恢复，再次批准必须走新版本 + 新预检 + 新审核完整链路（DM-005）。
7. **重复点击产生重复确认/重复预检/重复工单** —— 全部幂等（按钮受理即禁用 + 服务端幂等键）；重复确认不产生第二个有效人物选择（Issue #63 幂等合同）。

### 1.4 运营与审核人的交接

- 交接物是 **pending PlanReview（绑定具体 frozen 方案版本）**，不是聊天消息，与 A06 文案审核同一模式。
- 运营侧：预检满足提交门禁后「提交方案审核」是唯一交接动作；提交后版本只读、状态「审核中」。
- 审核人侧：在「审核」标签看到商品/文案/人物三段上游只读摘要、预检三组结论（含每条检查项）、输出说明、版本历史；批准或要求修改（意见必填）。
- 本人审核允许但必须标记：审核面板显示「本次为本人提交并审核（self_review）」记录条，不弱化、不额外阻断（与 A06 一致）。

## 2. 页面信息架构

### 2.1 结论：两个页面，分别对应阶段 3 与阶段 4

**评估与决定**：A07 的对象是人物目录与人物选择（跨项目可复用的资产视角 + 当前商品的选择状态），A08 的对象是绑定具体上游版本的不可变方案。两者对象集合、使用频率、使用者心智都不同：选人物是「从目录里挑一个」，做方案是「对固定组合做判断与决策」。塞进一页会让「换商品继续选人物」和「对某版本跑预检」互相干扰。LF-006/LF-007 也将其定义为两个阶段页面。因此：

- **页面一：人物与素材**（阶段 3，建议路由 `avatar.html`）：LF-006 三栏——左侧人物筛选与列表，中间人物预览与信息，右侧当前选择与可用性检查。
- **页面二：视频方案**（阶段 4，建议路由 `plan.html`）：延续 A04-A06 三栏工作台模式——左侧方案版本列表，中间方案摘要与输出说明，右侧「预检」与「审核」两个标签。
- **一个权威数据源**：所有状态从服务端读取；刷新/重进完整恢复（LF-012 轮询 + 手动刷新，Phase 1 不强制 WebSocket）。
- 两页共用：页头阶段条、商品上下文条（与 copy.html 同一结构，含商品切换器与上游摘要）；上游变化时的「需要重新确认」amber 阻断条。

### 2.2 页面结构

```text
壳层（左侧导航 + 顶部上下文栏，现有 shell，不重设计）
└── 页面内容区
    ├── 页头：面包屑 + 阶段条（A07 后阶段 3 可点；A08 后阶段 4 可点）
    ├── 商品上下文条：商品切换器 + 上游摘要（快照版本 / 文案批准状态 / 人物确认状态）
    └── 三栏工作区
        ├── avatar.html：人物筛选列表 | 人物预览与信息 | 当前选择与确认
        └── plan.html：方案版本列表 | 方案摘要与输出说明 | 预检 / 审核标签
```

为什么这样布局：

- **人物页左栏放目录而不是商品**：人物目录是「先选对象再操作」的导航；商品切换收进上下文条（与 A04-A06 决策 D3 一致），避免四栏。
- **人物页右栏放「当前选择与确认」而不是详情**：LF-006 明确右栏为当前选择和可用性检查；确认动作是门禁性决定，固定在最右决策栏，与审核类操作位置一致。
- **方案页完全复用 copy.html 三栏心智**：版本列表在左（不可变历史 + 当前草稿）、读写主对象在中、门禁与决策在右（预检/审核分标签，共享状态摘要条）。运营从文案页迁移到方案页零学习成本。
- **历史就近展示**：人物历史选择收进右栏折叠区；方案历史版本在左栏（灰、只读）；某版本的历次预检与历次审核收进右侧两个标签底部折叠区。历史永不静默覆盖。

### 2.3 对象组织

| 对象 | 位置 | 组织方式 |
|---|---|---|
| 商品 | 上下文条切换器（两页相同） | 下拉列表，按最近更新排序，每行：商品名（截断）+ 阶段状态摘要点 |
| 人物目录 | avatar.html 左栏 | 卡片式列表行：预览缩略 + 名称 + 来源（公共/企业）+ 业务可用 badge + 授权 badge；筛选：来源、可用状态；受控预置人物带「受控预置」标记 |
| 当前人物选择 | avatar.html 右栏 | 状态卡（未选择 / 已确认：人物名+版本+确认时间+确认人）+ 可用性检查清单 + 确认操作 + 历史选择折叠区 |
| 方案版本 | plan.html 左栏 | 版本行双行（版本号+创建时间一行，预检 badge+审核 badge 一行），与文案版本列表同构 |
| 上游引用 | plan.html 中栏 | 三张只读摘要卡：商品快照（版本+状态）、文案（版本+批准状态+当前有效性）、人物（版本+授权+能力摘要）；各带「返回对应阶段 →」链接（LF-018） |
| 输出说明 | plan.html 中栏 | draft 可编辑的唯一字段；frozen 只读；保存状态四态 |
| 预检 | plan.html 右栏「预检」标签 | 结论卡 → 三组检查（上游有效性/方案完整性/生产准备度）各成区块 → 历史预检折叠区 |
| 审核 | plan.html 右栏「审核」标签 | 当前审核状态卡 → 上游+预检摘要 → 操作区 → 审核历史列表（与 A06 ReviewPanel 同构） |

1. 状态判读（双 badge + 结论卡 / 可用性检查清单）永远可见，不需滚动；

| `version_conflict`（乐观并发 409） | 「此内容已被他人更新，你的修改未保存」 | amber blocked notice + 三选项：[查看最新版本] [复制我的修改] [放弃修改]；本地输入不清空（LF-016） | 用户显式三选一，绝不自动覆盖 |
| 未保存修改 | 「有未保存的修改」 | 输出说明底部状态行 amber 文字 + 离开前浏览器级提示 | 保存或放弃 |
| 空状态 | 人物页：「暂无可选人物」（真空）/「没有符合条件的人物」（筛选无结果 + [清除筛选]）；方案页：「还没有视频方案」+【创建视频方案】引导 | 三分类：真空 / 筛选无结果 / 加载失败（error notice + [重试]）；加载中骨架行 | 不显示「正在加载…」兜底 |
| 异步任务恢复 | 预检中离开再回来 | 状态全部由服务端重建；轮询 + 手动刷新 | 无假进度条 |

### 5.10 必须保持的关键区分（设计与文案双重保证）

1. **人物存在 ≠ 人物可用**：目录中出现只代表存在；可用性由业务状态 + 授权状态 + 能力 Evidence + 确认门禁共同决定，四者分开显示，不合并成一个「可用」。
2. **已验证能力 ≠ 全部能力**：能力摘要只列 Evidence 支持项；未验证能力灰色「未验证」，永不显示为支持；受控预置人物标注「Phase 1 受控预置」，不代表真实 Provider 能力 Evidence（D-030 §7）。
3. **Preflight passed ≠ PlanReview approved**：两 badge 永远并列（`(预检通过)(未提交审核)`）；「提交方案审核」按钮与确认文案含「人工审核」字样；approved 只来自人工操作。
4. **PreflightRun failed ≠ PreflightResult blocked**：技术失败 = 红 +「预检未完成（技术原因）」+ [重新预检]；业务阻断 = amber +「被阻断」+ 逐项指引，且结论卡注明「预检已于 11:21 完成」。颜色、文案、下一步完全不同。
5. **Local Agent 离线 ≠ 失败 ≠ 阻断**：只在 C 组生产准备度内显示 amber 提醒，文案明确「不影响方案审核」；页面级不红、不弹错误、不禁用任何保存/预检/审核按钮；失效传播矩阵中 Local Agent 离线不撤销 PlanReview（DM §24）。
6. **授权失效 ≠ 历史作废**：历史选择、历史方案、历史预检、历史批准全部只读保留；只有「新确认 / 新方案 / 新工单」被阻断。
7. **UI 投影标注**：「检查中」「审核中」「正在查看」「当前有效」均为投影或服务端计算结果；本设计未发明任何新领域状态，全部映射 D-028 §6、§11–§14。

## 7. 交互设计

### 7.1 筛选与浏览（A07）

- 筛选：来源与可用状态两个下拉即时生效；URL 不强制持久化（实现定）；筛选无结果显示「没有符合条件的人物」+ [清除筛选]，与真空区分。
- 排序：默认排序仅按名称/最近更新等中性规则，并在筛选条旁静态标注排序依据。**不得出现「推荐」「智能推荐」「猜你喜欢」等文案**——当前没有推荐算法合同与 Evidence 支撑，任何排序不得宣称智能（见 §10 D1）。
- 浏览不受门禁限制：文案无有效批准、人物不可用均可浏览与查看详情；门禁只拦「确认」动作（LF-006）。

### 7.2 确认与更换人物（A07）

- **确认**：选中可用人物 → 右栏【确认此人物】→ Dialog 摘要确认：人物名与版本、授权状态与有效期、已验证能力摘要、受控预置标记（如有）、当前文案版本引用 → 确认按钮「确认选择此人物」（实心主色）。一次显式确认，不叠加二次确认。
- **确认门禁**：Dialog 打开时与服务端命令执行时均由服务端重新验证门禁（文案批准仍有效、资产可用、授权有效、能力有 Evidence、本企业范围、素材可访问）；任一失败 → 命令被拒，Dialog 内 amber 逐条原因 + 返回权威阶段链接，绝不前端自放行。
- **幂等与防重复**：按钮受理即禁用；重复点击/刷新重进不产生第二个有效 AvatarSelection（Issue #63 幂等合同）；当前已确认人物与选中人物相同（同人物同版本）时，按钮禁用显示「当前已确认此人物」。
- **更换**：已有 confirmed 选择时确认不同人物 → Dialog 文案升级为更换确认，明确后果：「将创建新的人物选择，当前选择保留为历史；后续视频方案需基于新选择重新确认（产生新方案版本）」→ 确认后旧选择 `superseded`、新选择 `confirmed`，历史折叠区即时更新（不删除、不覆盖）。
- **过期授权 / 跨组织**：授权 `expired` 或 `incomplete` 的人物确认按钮禁用并说明原因与处理人；跨组织 ID 由服务端拒绝，前端显示业务文案「此人物不在本企业可用范围内」，不显示 403/错误码。
- **乐观并发**：选择确认携带基于版本；并发冲突（他人在期间确认/更换）→ amber blocked「人物选择已被他人更新」+ [查看最新选择]，不自动覆盖。

### 7.3 创建、保存、冻结方案（A08）

- **创建**：左栏【创建视频方案】→ 服务端基于当前 approved CopyVersion + confirmed AvatarSelection + 能力配置快照创建 draft 方案版本。上游任一无有效对象时按钮禁用并逐条说明（如「文案尚未批准 → 返回文案与质检」「尚未确认人物 → 返回人物与素材」），不创建缺输入的方案。
- **编辑**：draft 仅「输出说明」可编辑；上游引用永远只读，修改必须返回各自所属阶段（LF-007）。保存显式 [保存草稿]，保存状态四态（未保存/保存中/已保存 时间/保存失败保留本地输入 + [重试]）。
- **冻结**：[开始预检] 触发 draft → frozen + PreflightRun（服务端命令）；有未保存修改时禁用并提示「先保存」。
- **基于此方案修改**：frozen/历史版本的唯一演进路径；创建新 draft 版本（继承上游引用与输出说明为初始值），旧版本 `superseded`，旧预检/旧审核历史保留在旧版本上，不继承、不覆盖。
- **409 冲突**：与 A04-A06 一致的三选一恢复，本地输入在做出选择前不清空。

### 7.4 预检（A08）

- **运行**：[开始预检]/[重新预检] → 按钮 loading 受理即禁用 → 「预检中」信息蓝 +「可离开本页」说明；轮询恢复；无百分比、无假进度。
- **幂等**：同一方案版本重复触发预检不产生并行重复任务（服务端幂等，Issue #64）；已有进行中任务时入口禁用显示「已有预检进行中」。
- **结果呈现**：结论卡（badge +「预检已于 HH:MM 完成」）+ 三组检查区块。每条检查项：名称、结果（✓通过 / ⚠提醒 / ✗阻断）、原因、受影响对象与版本、下一步与「返回权威阶段 →」链接。
- **blocked**：结论卡 amber 加强左边框；「提交方案审核」禁用并逐条列出阻断项；无「强制通过」入口，管理员也不可绕过。
- **warning（含 Local Agent 离线）**：提醒项逐条列出，C 组提醒文案固定含「不影响方案审核」；若属允许审核的 warning，提交审核 Dialog 中复述提醒清单。
- **invalidated**：上游变化后（服务端判定）结论卡变 amber「已失效」+ 阻断条「上游已变化：文案批准已失效 / 人物授权已失效 / 商品快照已更新（按实际原因）」+ 下一步指引；历史预检进折叠区，永不覆盖。
- **技术失败**：红色「预检未完成（技术原因）」+ [重新预检]；与业务 blocked 严格区分（§5.10.4）。

### 7.5 审核（A08）

- **提交方案审核**：右栏「审核」标签主操作；禁用时逐条列出原因（如「预检被阻断：人物授权已失效」「存在未保存修改」）；提交 Dialog 摘要：方案版本、上游三引用、预检结论与提醒清单 → 确认按钮「确认提交人工审核」。提交后版本只读、状态「审核中」。
- **批准**：审核人看到上游三摘要 + 输出说明 + 预检三组结论 + 版本历史；[批准方案] 实心主按钮 → 单 Dialog 摘要确认（被批准对象：版本号 + 预检结论 + 上游引用快照，确认按钮「确认批准」）。服务端批准前重新验证预检/上游/权限；前端只发命令。
- **要求修改**：[要求修改]（次按钮）→ Dialog 意见必填（空时确认禁用）→ `changes_requested`；运营视角 amber + 意见全文 +「基于此方案修改」入口。
- **self_review**：提交人与审核人相同时显示「本人提交并审核（self_review）」，不阻断。
- **上游变化撤销**：服务端撤销后页面显示 amber 阻断条「批准已失效：<变化类别>，需重新预检并重新审核」+ 审核历史 revoked 记录（含时间与原因）；旧记录不删除、不恢复；再次批准必须走新版本 + 新预检 + 新 Review 完整链路（DM-005）。
- **重复操作幂等**：提交/批准按钮受理即禁用；重复提交返回原结果，不产生第二个并行 pending PlanReview（Issue #64 幂等合同）。

### 7.6 危险操作与 Dialog 使用（低打扰原则）

| 操作 | 是否 Dialog | 理由 |
|---|---|---|
| 确认人物 | 是（摘要确认） | 门禁性决定，一次摘要确认防误触 |
| 更换人物 | 是（摘要确认 + 后果说明） | 影响下游方案有效性，必须写明后果 |
| 提交方案审核 | 是（摘要确认） | 交接动作，摘要含预检提醒清单 |
| 批准方案 | 是（摘要确认） | 门禁性决定；不叠加二次确认 |
| 要求修改 | 是（意见表单） | 意见必填，表单即确认 |
| 保存/开始预检/重新预检/清除筛选 | 否 | 可逆或有后续门禁兜底，按钮受理态即反馈 |
| 版本切换（有未保存修改） | 否（就地 notice） | 用就地提示替代模态打断 |

### 7.7 终态边界

前端只发业务命令（确认人物选择/创建方案/保存草稿/开始预检/提交方案审核/批准方案/要求修改），**永不直接写 `confirmed`/`passed`/`approved` 等终态**；所有 badge 与结论来自服务端响应；异步进行中只有「等待」投影，不做乐观完成。

## 8. 动效设计

全部使用既有 token：`--motion-fast: 140ms`、`--motion-panel: 220ms`、`--ease-out: cubic-bezier(0.2, 0, 0.38, 1)`。时长区间 120–240ms，ease-out，无弹簧/回弹/循环。

| 场景 | 动效 | 时长 |
|---|---|---|
| 保存成功 / 状态 notice 出现 | opacity 淡入（既有 `notice-in`） | 150ms |
| 状态 badge 变化（待确认→已确认、未预检→预检中→通过/提醒/阻断） | 颜色 cross-fade | 120ms |
| 人物列表插入/筛选重排、版本列表插入新版本 | 单次淡入，无位移弹跳 | 140ms |
| Dialog / 移动端人物抽屉 / 版本抽屉 | opacity + translateY(8px→0)（既有 `dialog-in`） | 200–220ms |
| 选中人物行 / 选中版本行 / 标签切换 | 背景色、边框色过渡 | 120–150ms |
| 检查清单项在确认门禁刷新后更新 | 颜色 cross-fade 单次 | 120ms |
| 列表骨架（加载中） | 静态灰条或单次淡入 | — |

明确禁止：虚假进度条（预检中只显示状态 badge，不显示百分比）；循环呼吸/脉冲；数字滚动；位移动画引起的布局跳动；任何 > 240ms 的动效；把等待动画当作成功证据。

**prefers-reduced-motion**：沿用 base.css 既有 media query（全部 transition/animation 压至 0.01ms）；本两页补充——抽屉/对话框改为瞬时显隐、spinner 换静态「处理中…」文案、骨架不闪烁；状态信息永不依赖动效传达（badge 颜色 + 文字双编码）。
