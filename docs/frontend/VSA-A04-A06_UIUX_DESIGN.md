## 0. 输入与边界确认

- 视觉基线：冷中性灰 + 品牌蓝 `#1769e0`，token 以 `web/tokens.css` 为准；控件样式以 `web/base.css` 为准；壳层以 `web/shell.css` / `web/shell.js` 为准。本设计只引用这些既有变量与组件，不新增色值、字体、圆角（上限 8px）和阴影级。

## 1. 用户工作流分析

### 1.1 进入原因与任务

| 角色 | 进入原因 | 要完成的任务 |
|---|---|---|
| 运营 | 商品快照已 Ready，需要出文案 | 生成文案 → 编辑确认 → 启动质检 |
| 运营 | 质检有问题 | 逐项处理 Finding：修改正文（新版本）、接受提醒（填理由）、AI 改写、退回补充商品事实 |
| 运营 | 文案被打回 | 查看审核意见 → 修改产生新版本 → 重新质检 → 重新提交 |
| 运营 | 日常巡检 | 扫多个商品的文案状态，找到「待我处理」的版本 |
| 审核人 | 有 pending 审核 | 对照商品事实摘要、质检结论、Finding 处理记录 → 批准或要求修改（必填意见） |

主链路（单商品）：**输入（上游商品快照，只读引用）→ 生成（异步，可离开）→ 查看（版本列表 + 正文）→ 修改（draft 编辑 / frozen 创建新版本）→ 确认（启动 QC → 处理 Finding → 提交审核）→ 人工审核（批准 / 要求修改）→ 下一阶段（人物与素材，A07，链接在批准后出现）**。

### 1.2 最高频动作（按优先级排序，决定布局与默认焦点）

1. 扫版本列表，确认「当前版本到哪一步了」（QC 状态 + 审核状态双 badge）。
2. 编辑正文并保存（draft 阶段）。
3. 逐项处理 Finding（needs_review 的逐条接受/改写/退回）。
4. 审核人批准 / 要求修改。
5. 切换商品继续处理下一件。

### 1.3 最危险的误操作（按后果排序，决定确认层级与禁用策略）

1. **把 QC passed 当成已批准**进入下一阶段 —— 用双 badge 并列 + 提交审核前明确文案阻断（见 §5）。
2. **并发编辑静默覆盖他人修改** —— 乐观并发 + 409 冲突三选一恢复，绝不自动覆盖（LF-016、D-028 §25）。
3. **把 blocked 当成技术失败反复重跑 QC** —— blocked（业务阻断）与 qc_failed（技术失败）用不同颜色、不同下一步（§5.5）。
4. **不填理由接受 Finding / 不填意见打回** —— 理由与意见为必填表单，服务端校验，前端禁用空提交。
5. **用历史批准套用新版本** —— 领域已禁止；界面上新版本永远显示「未提交审核」，旧版本的批准 badge 只留在旧版本行上。

### 1.4 运营与审核人的交接

- 交接物是 **pending HumanReview（绑定具体 frozen 文案版本）**，不是聊天消息。
- 运营侧：QC 满足提交门禁后，「提交审核」是唯一的交接动作；提交后版本进入「审核中」，运营只读等待或继续处理其他商品。
- 审核人侧：在同一工作区「审核」标签看到商品事实摘要、正文、QC 结论、Finding 处理记录（含理由）、版本变化与历史；批准或要求修改。
- 审核结论回传运营：`approved` → 版本列表出现「当前有效」与「进入人物与素材」入口；`changes_requested` → amber「要求修改」+ 意见全文，下一步是创建新版本。
- 本人审核允许但必须标记：审核面板显示「本次为本人提交并审核（self_review）」记录条，不做视觉弱化，也不做额外阻断（D-028 §9）。

## 2. 页面信息架构

### 2.1 结论：一个「文案与质检」权威工作区覆盖 A04-A06

**评估与决定**：A04（生成与版本）、A05（QC 与 Finding）、A06（人工审核）操作同一组对象（CopyVersion 及其 QC/Review 记录），状态强耦合（QC 结论决定审核门禁，审核结论决定业务有效性）。拆成三个页面会强迫用户在页面间跳转核对「这个版本的 QC 过了没有、审了没有」，违背状态优先与可扫描原则。LOW_FI LF-005 也将其定义为**一个三栏工作台**。因此：

- **一个页面**：项目五阶段之「文案与质检」工作区（建议路由 `copy.html`，见 §9）。
- **一个权威数据源**：所有状态从服务端读取；QC、审核、版本列表是同一版本对象的不同侧面，在页面内分区展示，不做跨页同步。
- **A04-A06 按列增量落地**：A04 交付左栏 + 中栏（生成/版本/编辑闭环）；A05 加入右栏「质检」标签；A06 加入右栏「审核」标签。布局网格随 Slice 从两栏扩为三栏，不提前渲染占位假面板（见 §9.5）。

### 2.2 页面结构

```text
壳层（左侧导航 + 顶部上下文栏，现有 shell，不重设计）
└── 页面内容区
    ├── 页头：面包屑 + 阶段条 + 页级主操作区
    ├── 商品上下文条：商品切换器 + 当前 ProductRevision 摘要
    └── 三栏工作区
        ├── 左栏：文案版本列表（不可变历史 + 当前草稿）
        ├── 中栏：文案正文编辑 / 只读查看 / 版本对比
        └── 右栏：「质检」与「审核」两个标签（共享状态摘要条）
```

为什么这样布局：

- **左栏放版本而不是商品**：LF-005 明确左栏为不可变文案版本列表。版本是「先选对象再操作」的导航，符合列表-详情模式；版本数量通常个位数到十几，264px 窄栏足够。
- **大量商品靠上下文条而不是第三列表**：若左栏再放商品列表，三栏会变成四栏，正文编辑区被挤压到不可用。商品切换收进页头下的上下文条（下拉选择器，含每商品的 QC/审核摘要标记），切换商品 = 刷新整个工作区上下文。项目级跨商品总览属于项目工作台（阶段一页面）与后续批量能力，不在本页（决策见 §10 D2）。
- **中栏最宽留给正文**：文案正文是读写主对象；编辑、只读历史、对比三种模式共用同一区域，避免多窗口。
- **右栏放门禁与决策**：QC 与审核是「对当前版本的判断」，宽度 384px 容纳 Finding 卡片；两个标签共享一条状态摘要（QC badge + 审核 badge 常显），切标签不丢上下文。质检与审核分标签而不是上下堆叠：Finding 多时堆叠会把审核区推到不可见位置，且两者使用者不同（运营 vs 审核人）。
- **历史就近展示**：历史版本在左栏（灰、只读）；某版本的历次质检收进「质检」标签底部折叠区；历次审核记录收进「审核」标签底部列表。历史永不被静默覆盖，只读模式有明确横幅。

### 2.3 对象组织（大量商品 / 版本 / QC / 审核 / 历史）

| 对象 | 位置 | 组织方式 |
|---|---|---|
| 商品 | 上下文条切换器 | 下拉列表，按最近更新排序，每行：商品名（截断）+ 状态摘要点；当前商品名截断 + title |
| 当前商品/版本上下文 | 上下文条 + 中栏标题行 | 商品快照版本（如「商品快照 v3 · 已 Ready」）、文案版本号、来源、生命周期 badge |
| 编辑区 | 中栏 | draft 可编辑；frozen/历史只读 + 「基于此版本修改」入口 |
| QC | 右栏「质检」标签 | 结论卡（badge + 说明 + 主行动）→ Finding 卡片列表（未处理在前）→ 历史质检折叠区 |
| 审核 | 右栏「审核」标签 | 当前审核状态卡 → 事实/QC/Finding 摘要 → 操作区 → 审核历史列表 |
| 历史 | 左栏版本列表 + 右栏两个折叠区 | superseded/revoked 全部保留可查看，只读 |

### 3.3 页级主操作唯一化规则（每屏仅一枚实心品牌色按钮）

| 当前上下文 | 主操作【主】 | 同屏次操作 |
|---|---|---|
| 无版本 / 可再次生成 | 生成文案（左栏顶部） | — |
| draft 有未保存修改 | 保存草稿 | 开始质检（禁用，提示「先保存」）、对比版本 |
| draft 已保存 | 开始质检 | 保存草稿（禁用，无修改）、对比版本 |
| 生成中 / 质检中 | 无主操作（badge + 说明文案） | 对比版本 |
| QC needs_review 且全部 Finding 已处理 / QC passed | 提交审核（右栏审核标签） | 对比版本 |
| 审核 pending（审核人视角） | 批准文案（右栏审核标签） | 要求修改（次按钮， amber 语义但不实心包） |
| 已批准且当前有效 | 进入人物与素材 →（主按钮样式的导航链接） | 对比版本 |
| 只读历史版本 / 无权限 | 无主操作 | 基于此版本修改（历史）/ 全部禁用带说明 |

### 3.4 主要交互优先级

1. 状态判读（双 badge + 结论卡）永远可见，不需滚动；
2. 当前下一步动作（主操作）在视口内且不移动位置（编辑区操作行固定在正文下方，右栏操作在结论卡内）；
3. Finding 处理操作在卡片内就地完成，不跳页；
4. 低频操作（对比版本、历史质检、生成入口在已有进行中任务时）降为次按钮或折叠。

## 4. 390px 移动端方案

原则：无横向滚动（全局 `overflow-wrap: anywhere` 已由 base.css 提供）；栏从三栏变单栏堆叠；高频对象（正文、Finding）优先，导航对象（版本列表、商品切换）折叠。

### 4.1 折叠/保持/变形清单

| 桌面元素 | 390px 处理 |
|---|---|
| 壳层导航 | 现有行为：顶部 48px 横向滚动导航（不重设计） |
| 阶段条 | 收缩为一行「阶段 2/5 · 文案与质检」，tap 展开纵向阶段列表（details 式展开，非新组件）；不做横向滚动长条 |
| 商品上下文条 | 保持一行：商品切换器占满宽度（100% - 16px），快照 badge 换行到第二行；吸顶保留 |
| 左栏版本列表 | **变抽屉/折叠条**：正文上方一行「v4 · 草稿 · AI 生成 ▾」，tap 展开全屏抽屉（复用 Dialog 的遮罩与动效规格，max-height 80dvh）选择版本；生成文案入口在抽屉顶部 |

### 4.3 长文本策略

- 长商品名：切换器内单行截断 + title；上下文条第二行不截断快照信息。
- 长文案：textarea 内部滚动，页面上方「版本抽屉条」吸顶保留上下文；只读模式自然换行（`overflow-wrap: anywhere`）。
- 长 Finding：卡片内全部字段自然换行；命中文本用引号块，最长两行后「展开」；原因/建议不截断（决策所需信息不得藏在 title 里）。

## 5. 状态设计

颜色语义严格映射 `tokens.css`：成功绿（success）、提醒 amber（warning）、失败红（danger）、失效灰（inactive = N 系纯灰）、进行中信息蓝（progress）。红只给失败与危险确认，绝不给等待/待处理/阻断（Stage 0 §5.4 红线）。

### 5.1 CopyVersion 生命周期（领域持久状态，D-028 §7）

| 状态 | 中文文案 | 颜色语义 | 下一步操作 |
|---|---|---|---|
| `draft` | 草稿 | 中性灰（默认 `.state`） | 编辑并保存；保存后可「开始质检」 |
| `frozen` | 已冻结 | 中性灰 + 「已锁定」辅助说明 | 查看 QC/审核进度；「基于此版本修改」创建新草稿 |
| `superseded` | 已被替代 | 失效灰 | 只读查看；可复制内容形成新版本（需完整重新 QC） |

### 5.2 生成与质检执行（AsyncJob / QualityRun 的 UI 投影，非业务结论）

> 以下为 **UI 投影**：领域持久状态在 AsyncJob/QualityRun 上，不写入 CopyVersion。前端轮询/刷新以服务端为准，永不自造终态。

| 投影 | 中文文案 | 颜色语义 | 下一步操作 |
|---|---|---|---|
| 生成排队/进行中（`generating`） | 生成中，可离开本页 | 信息蓝 | 等待；可切换商品或离开，回来后状态从服务端恢复 |
| 生成完成（`generated`，瞬时投影） | 已生成，尚未质检 | 一次性成功绿 toast + 版本行「草稿」badge | 不是持久状态：生成成功落为 `draft`；下一步是检查正文、保存、开始质检；**不得显示为「质检通过」或任何审核态** |
| 生成失败（`generation_failed`） | 生成失败，未产生文案 | 失败红 | [重试生成]；持续失败 → 返回商品与目标检查输入 |
| 质检进行中（`checking`） | 质检中 | 信息蓝 | 等待，可离开 |
| 质检技术失败（`qc_failed`） | 质检未完成（技术原因） | 失败红 | [重新质检]；不显示为内容问题 |

### 5.3 QualityResult（领域持久、不可变，D-028 §8）

| 状态 | 中文文案 | 颜色语义 | 下一步操作 |
|---|---|---|---|
| `invalid` | 质检结果无效 | 提醒 amber | [重新质检]；说明「本次质检未得到可信结果，需重新执行」 |
| `blocked` | 存在硬阻断 | 提醒 amber（结论卡加强左边框 + 全文说明） | 修改文案（新版本）或返回补充/修正商品事实后**完整重新质检**；不可提交审核，管理员也不可绕过；界面不提供任何「强制通过」入口 |
| `needs_review` | 待人工判断（N 条） | 提醒 amber | 逐项处理 Finding；处理完后「提交审核」 |
| `passed` | 质检通过 | 成功绿 | 「提交审核」；badge 旁必须同时显示审核状态（避免误读为已批准） |

### 5.4 QualityFinding 处理状态（领域持久，D-028 §8）

| 状态 | 中文文案 | 颜色语义 | 说明 |
|---|---|---|---|
| `unresolved` | 待处理 | 提醒 amber | 卡片默认展开，操作：定位 / 人工修改 / 接受（填理由）/ AI 改写 / 退回商品事实 |
| `accepted_with_reason` | 已接受（附理由） | 中性灰 + 已解决样式 | 理由全文可见；处理人、时间可见 |
| `change_requested` | 已要求修改 | 中性灰 | 引导创建新版本；新版本重新质检后该 Finding 历史保留 |
| `returned_to_facts` | 已退回补充事实 | 中性灰 | 附「返回商品与目标」链接（LF-018） |
| `superseded` | 已失效 | 失效灰 | 版本或规则变化后保留历史，不删除 |

### 5.5 HumanReview（领域持久、不可变，D-028 §9）

| 状态 | 中文文案 | 颜色语义 | 下一步操作 |
|---|---|---|---|
| `not_submitted` | 未提交审核 | 中性灰 | 满足门禁后「提交审核」；不满足时按钮禁用并逐条说明原因（可以是服务端计算的界面状态，不强制存在空 Review 行） |
| `pending`（`reviewing` 投影） | 审核中 | 信息蓝 | 运营：等待；审核人：批准 / 要求修改 |
| `approved` | 已批准 | 成功绿 | 「进入人物与素材 →」；同时显示「当前有效」投影 |
| `changes_requested`（`requires_action` 语义） | 要求修改 | 提醒 amber | 查看意见 → 修改产生新版本 → 重新 QC → 重新提交；**amber 不是失败**，是人工流程的正常回路 |
| `revoked` | 已撤销 | 失效灰 + 原因说明 | 不可恢复；需在新版本/新 QC 后创建**新**审核（DM-005）；历史记录完整保留可查 |

### 5.6 业务可用性投影（服务端计算，D-028 §10，非持久字段）

| 投影 | 中文文案 | 颜色语义 | 展示位置 |
|---|---|---|---|
| `current_valid` | 当前有效 | 成功绿 | 版本列表行 + 中栏标题行；含义「可进入下一阶段」 |
| `invalidated` | 已失效（上游已变化） | 提醒 amber | 版本行 + 编辑区顶部阻断条：「商品事实已更新，此版本的质检与批准已失效」+ 下一步指引 |
| `approval_revoked` | 批准已失效 | 提醒 amber | 审核标签 + 版本行；说明哪类上游变化导致（商品名称/卖点/图片/ContentBrief/品类/规则版本），提供「基于最新事实重新生成/修改」入口 |
| `selected` / 当前版本 | 当前版本 | 品牌蓝 tint（列表行标记，非语义色） | **UI 投影**：左栏当前选中查看的版本；与服务端「当前有效」是两个概念，列表中「当前有效」用绿 badge、「正在查看」用行选中样式，不混用 |

### 5.7 页面级状态

| 状态 | 中文文案 | 呈现 | 下一步 |
|---|---|---|---|
| `no_permission`（已登录但无权限） | 「你可以查看，但没有审核/生成权限」 | amber blocked notice + 相关按钮禁用并附原因；业务语言，不出现 403/RBAC；只读视图保留 | 「请联系管理员或有审核权限的成员处理」 |
| `version_conflict`（乐观并发 409） | 「此内容已被他人更新，你的修改未保存」 | amber blocked notice（`.notice.blocked`）+ 三选项：[查看最新版本] [复制我的修改] [放弃修改]；本地输入不清空（LF-016） | 用户显式三选一，绝不自动覆盖 |
| 未保存修改 | 「有未保存的修改」 | 编辑区底部状态行 amber 文字 + 离开页面前浏览器级提示 | 保存或放弃 |
| 空状态 | 「还没有文案」 | 真空：一句话 + 【生成文案】引导；加载失败：error notice + [重试]；加载中：骨架行 | 不显示「正在加载…」兜底 |

### 5.8 必须保持的关键区分（设计与文案双重保证）

1. **生成成功 ≠ QC passed**：生成完成只产生「草稿」badge + toast；QC 状态独立显示「未质检」。文案：「文案已生成，尚未质检。」
2. **QC passed ≠ approved**：两 badge 永远并列展示（`(质检通过)(未提交审核)`）；「提交审核」主操作的按钮文案与确认文案均含「提交人工审核」字样；approved 只来自人工操作。
3. **QualityRun failed ≠ QualityResult blocked**：技术失败 = 红 + 「质检未完成（技术原因）」+ [重新质检]，无新业务结论；业务阻断 = amber + 「存在硬阻断」+ 修改指引，QC 本身执行成功。两者颜色、文案、下一步完全不同，且在结论卡中注明「质检已于 14:03 完成」（blocked）或「质检未完成」（failed）。
4. **requires_action ≠ failed**：要求修改/待处理统一 amber、文案强调「下一步由谁做什么」；红只保留给真实失败（生成失败、质检技术失败、保存失败）。
5. **UI 投影标注**：`generating`/`checking`/`reviewing`/`selected`/「当前有效」均为投影或服务端计算结果，不是 CopyVersion 生命周期状态；本设计未发明任何新领域状态，全部映射 D-028 §7-§10。

## 7. 交互设计

### 7.1 生成（A04）

- 点击【生成文案】→ 按钮立即 loading（spinner + 禁用，文案不变）→ 服务端受理后进入「生成中」信息蓝 badge + 说明「生成中，可离开本页，完成后状态自动更新」。
- **幂等**：按钮受理后禁用；重复点击/刷新重进不产生第二个任务（服务端幂等键，Issue #60 合同）；已有进行中任务时入口禁用并显示「已有生成任务进行中」。
- **允许离开 / 重新进入恢复**：页面状态全部由服务端重建；定时轮询 + 手动刷新（Phase 1 不强制 WebSocket，LF-012）。
- **失败**：error notice「生成失败，未产生文案」+ [重试生成]；重试受控（遵循 D-023 最多一次自动重试后的手动重试），不自动换模型/Provider，界面不暴露 Provider。
- **取消**：Phase 1 不提供用户主动取消（AsyncJob 生命周期由服务端管理）；长时间未完成显示「生成时间较长，可稍后回来查看」，不显示虚假进度。
- 生成完成：toast「文案已生成，尚未质检」+ 左栏插入新版本行（列表顶部）+ 自动选中新版本。

### 7.2 编辑、保存、冻结、版本切换、对比、冲突（A04）

- **编辑**：仅 `draft` 可编辑；frozen/历史版本只读，顶部灰条说明「此版本已冻结，修改将创建新版本」+ [基于此版本修改]。
- **保存**：显式 [保存草稿]；保存状态行四态（未保存/保存中/已保存 时间/保存失败）；保存失败保留本地输入 + error notice + [重试]。
- **冻结**：[开始质检] 触发 draft → frozen（服务端命令）；冻结前若有未保存修改，按钮禁用并提示「先保存」。
- **版本切换**：左栏点击即切换；有未保存修改时切换前触发保存提示（就地 notice，不用浏览器 confirm）；任何正文变化都通过「保存（draft）」或「基于此版本修改（新 draft）」显式发生，不存在静默覆盖。
- **对比**：选择任意两个版本进入对比视图（中栏模式切换）；对比视图只读；历史版本永远可查，不删除。
- **version_conflict 恢复**：409 → blocked notice「此内容已被他人更新，你的修改未保存」+ [查看最新版本]（加载最新，保留本地草稿于可复制的暂存区）[复制我的修改]（复制到剪贴板）[放弃修改]（重载服务端版本）；三选一显式执行，本地输入在做出选择前不清空。

### 7.3 QC 与 Finding（A05）

- **启动 QC**：[开始质检] → frozen + QualityRun；进行中信息蓝；完成后 QC 结论卡更新（状态 cross-fade）。
- **Finding 逐项处理**（禁止「忽略全部/接受全部」入口）：
  - [定位]：中栏滚动到命中段并高亮（≤ 240ms，reduced-motion 下直接定位不高亮）；
  - [接受]：打开理由 Dialog，理由必填（空时确认按钮禁用），提交后卡片标「已接受」并显示理由、处理人、时间；
  - [人工修改]：引导「基于此版本修改」创建新 draft（旧 Finding 保留于旧版本）；
  - [退回商品事实]：确认后标记 `returned_to_facts` + 提供「返回商品与目标」链接；实际属于未确认事实的问题不提供「接受」路径（服务端门禁，前端隐藏该选项并说明原因）；
  - **blocked Finding 卡片不提供「接受」**，只提供修改/退回事实路径，并注明「硬阻断不可人工绕过」。
- **AI 改写**：从 Finding 卡片 [AI 改写] 进入 Dialog：勾选改写范围（命中段/全文的业务选项）+ 业务指令输入（自由文本创作说明，**无 Prompt 编辑器**）→ 异步生成 → **新 CopyVersion 草稿 + 自动完整重新质检**；不覆盖旧版本、不继承旧 QC 与旧批准；进行中状态与生成一致（信息蓝、可离开）。
- **重新质检**：`invalid`/技术失败/内容修改后，[重新质检] 创建新 QualityRun 与新 QualityResult；旧结果进「历史质检」折叠区，永不覆盖。

### 7.4 审核（A06）

- **提交审核**：右栏「审核」标签主操作；禁用时逐条列出原因（如「2 条 Finding 待处理」「质检已失效：商品事实已更新」）；提交后版本只读、状态「审核中」。
- **批准**：审核人看到商品事实摘要 + 正文 + QC 结论 + Finding 处理记录（含理由）+ 版本历史；[批准文案] 为实心主按钮，点击后单 Dialog 确认（列出被批准对象：版本号 + QC 结论 + Finding 处理摘要，确认按钮「确认批准」）。服务端批准前重新验证 QC/上游/权限；前端只发命令。
- **要求修改**：[要求修改]（次按钮）→ Dialog 意见必填 → `changes_requested`；运营视角显示 amber + 意见全文 + 「创建新版本」入口。
- **self_review**：提交人与审核人相同时，审核历史与当前状态卡显示「本人提交并审核（self_review）」，不阻断。
- **上游变化撤销批准**：服务端撤销后，页面（刷新/轮询后）显示 amber 阻断条「批准已失效：<变化类别>，需重新质检并重新审核」+ 审核历史中 revoked 记录（含时间与原因）；旧记录不删除、不恢复；再次批准必须走新版本 + 新 QC + 新 Review 完整链路。
- **重复操作幂等**：批准/提交按钮受理后禁用；重复提交返回原结果，不产生第二个人 Review（Issue #62 合同）。

### 7.5 危险操作与 Dialog 使用（低打扰原则）

| 操作 | 是否 Dialog | 理由 |
|---|---|---|
| 接受 Finding | 是（理由表单） | 理由必填，表单即确认；一步完成 |
| 要求修改 | 是（意见表单） | 意见必填 |
| 批准文案 | 是（摘要确认） | 门禁性决定，一次摘要确认防误触；不叠加二次确认 |
| AI 改写 | 是（指令表单） | 需要输入指令，表单即确认 |
| 手动撤销批准（若实现该命令） | 是（危险确认） | 写明对象与后果「批准记录将保留但不再有效」，确认按钮实心红「确认撤销」 |
| 生成/保存/开始质检/提交审核/重试 | 否 | 可逆或有后续门禁兜底，按钮受理态即反馈，不打断高频流 |
| 版本切换（有未保存修改） | 否（就地 notice） | 用就地提示替代模态打断 |

### 7.6 终态边界

前端只发业务命令（生成/保存/开始质检/处理 Finding/AI 改写/提交审核/批准/要求修改），**永不直接写 `passed`/`approved`/`succeeded` 等终态**；所有 badge 与结论来自服务端响应；异步进行中只有「等待」投影，不做乐观完成。

## 8. 动效设计

全部使用既有 token：`--motion-fast: 140ms`、`--motion-panel: 220ms`、`--ease-out: cubic-bezier(0.2, 0, 0.38, 1)`。时长区间 120–240ms，ease-out，无弹簧/回弹/循环。

| 场景 | 动效 | 时长 |
|---|---|---|
| 保存成功 / 状态 notice 出现 | opacity 淡入（`notice-in` 既有） | 150ms |
| 状态 badge 变化（草稿→质检中→待处理→已通过） | 颜色 cross-fade | 120ms |
| 版本列表插入新版本 / Finding 卡片标记已处理 | 单次淡入，无位移弹跳 | 140ms |
| Dialog / 移动端版本抽屉 | opacity + translateY(8px→0)（`dialog-in` 既有） | 200–220ms |
| 选中版本行 / 标签切换 | 背景色、边框色过渡 | 120–150ms |
| Finding [定位] 命中段高亮 | 背景色淡入后淡出一次（单次，不循环） | 240ms 内 |
| 列表骨架（加载中） | 静态灰条或单次淡入 | — |

明确禁止：虚假进度条（生成/质检进行中只显示状态 badge，不显示百分比）；循环呼吸/脉冲 spinner 以外的旋转（spinner 仅限按钮内 14px 线性旋转）；数字滚动；位移动画引起的布局跳动；任何 > 240ms 的动效。

**prefers-reduced-motion**：沿用 base.css 既有 media query（全部 transition/animation 压至 0.01ms）；本页补充——命中段高亮改为静态描边或纯定位滚动、spinner 换静态「处理中…」文案、骨架不闪烁；状态信息永不依赖动效传达（badge 颜色 + 文字双编码）。
