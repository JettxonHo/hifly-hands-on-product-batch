## 回执与稳定关联设计

沿用现有对象，用户所说的Workspace Job以既有ProductionOrder为业务入口，不新增Job表或执行器：

`ProductionOrder → ExecutionAttempt/冻结输入 → Hifly提交回执 → Hifly Task/Work → 原片候选 → Report/A12 → Work/交付片`

- 提交前持久保存已有attempt/输入版本与一次提交标记，并建立本次提交的观察器；本地receipt标记仅用于关联，不能冒充飞影回执。
- 从同一次真实UI提交的权威响应/事件取得可查询的Provider实体ID，明确它是task、work还是project；Project ID或HTTP request-id单独存在不够。
- 用该ID只读查询同一结果，核对完成状态及media ID/结果地址，再定向下载；禁止通过最新作品、列表第一条、名称/时间或最后下载文件认领结果。
- 在现有不可变Report中保存脱敏Provider回执与实体引用，再由Work引用该Report；原片和交付片各自保留文件完整性与任务绑定。签名URL/会话信息不入公共记录。

当前 `submissionReceiptResolver` 只有调用与失败关闭入口，缺真实实现和本次可核验来源；内部task_id、handoff job/receipt、拼接asset_id均不是飞影ID。当前Cloud结果也尚未把Provider回执持久传入Report/Work。**关联机制尚为设计，未标PASS。** 最小工程工作只是在确认真实回执结构后接入已有入口与Report，不新建关联平台。若平台不给可可靠关联的ID，保持BLOCKED并明确请求平台支持，不能降级为列表差。

2026-09-09另行核对[官方API V2文档](https://api.lingverse.co/hifly.html)：官方口播视频接口返回task_id，查询/回调提供状态、时长和临时视频地址，可作为官方API路径的关联依据。但文档中的图片数字人输入只有单张图，未确认“人物图＋商品图合成手持效果”的接口；不能把普通图片数字人/口播API视为完整手里有货。项目官方client目前只查积分和公共人物目录，未接生成/任务查询/下载；线上App只读检查HIFLY_API_TOKEN存在性为false，生产执行保持停用。API能力与本轮路径的进一步选择见既有[能力证据台账](../product/HIFLY_CAPABILITY_EVIDENCE.md)，本次不切换执行器或扩大功能。

同日公开前端核对进一步确认：goods用网页CMS的两图合成接口，再把gen_id/image_oss_key传给商品视频接口；不是前端直接调用公开V2的create_by_image/create_by_tts。后台是否共用服务/模型及开发者Token能否使用这些能力仍未知。提交响应的通用埋点提供id/creation_id/task_id候选线索，当前真实schema未验证，不能把它们直接写成可靠回执。Owner偏好完整官方API路线；仅替换后半段不能当作完整API闭环，当前上传/生成/预算门禁不变。
