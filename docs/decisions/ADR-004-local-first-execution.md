# ADR-004: 本地优先执行架构（原 ADR-001；已由 D-034 supersede）

> 编号说明：本决策创建于 2026-08-01。2026-07 创建的 Playwright/Capture HTTP 决策已保留 ADR-001/ADR-002；为消除历史重复编号，本文件现统一为 ADR-004。

- **状态**：Superseded by D-034（2026-08-12）
- **日期**：2026-08-01
- **决策者**：项目 owner + 执行代理共识

## 背景

飞影「手里有货」批量视频生产依赖浏览器自动化（Playwright）操作 `hifly.cc/goods` 页面。当前链路为：

```
本地 GUI → 本地 Fastify → 本地批次文件/状态机 → Playwright 持久化浏览器 → 飞影网页
```

## 决策

当前版本继续使用本地优先执行架构，不迁移到 React、TypeScript、微服务或云原生架构。

## 原因

1. **登录态需要持久化浏览器 profile**：飞影登录态存储在 Playwright 的 `playwright/profile/` 目录中，依赖本地文件系统。Serverless 环境无法保持持久化浏览器实例。
2. **飞影流程时间长**：单条视频生成 5-6 分钟（340s+），超出大多数 Serverless 函数的执行时限。
3. **本地文件依赖**：批次状态 (`batch.json`)、上传副本、视频产物均存储在本地文件系统，不适合直接迁入无状态服务。
4. **当前不迁移技术栈**：vanilla HTML/CSS/JS 零构建 GUI 已满足需求，引入框架会增加构建复杂度和维护成本，无明确收益。
5. **Capture HTTP 仅作为实验路径**：API 直调虽更稳定，但 manifest 维护成本高、飞影接口变化风险大，暂不替代 Playwright。

## 后果

- 优点：架构简单、调试直观、无云服务成本、登录态管理简单。
- 缺点：无法水平扩展执行节点、无法远程访问 GUI、依赖用户本机运行。

## 重新评估触发条件

- 单用户日产量超过 50 条视频且本机资源成为瓶颈。
- 需要多人协作远程访问同一批次。
- 飞影开放官方 API 使 Playwright 不再必要。
